# llm-serving-lab 설계 명세

날짜: 2026-09-09  
상태: 2026-09-10 사용자 검토·승인 완료 — 구현 전

## 이 문서 읽는 법

이 문서는 **개발할 때 무엇을 만들고, 어떻게 동작해야 하는지 정한 약속**입니다. 서비스의 쉬운 설명은 [입문 안내](../../introduction.md), 선택 이유는 [의사결정 기록](../../decisions/README.md)에 있습니다.

핵심 흐름은 “문서를 받는다 → 나누어 저장한다 → 질문과 관련된 부분을 찾는다 → AI가 답한다”입니다. 아래의 기술적인 규칙은 이 과정에서 기다림·오류·정보 유출을 어떻게 다룰지 구체적으로 적은 것입니다.

## 1. 목표와 성공 기준

Python 백엔드 경험을 Production LLM Serving 영역으로 확장한다. 한국어 문서 RAG를 실제 워크로드로 사용하고 외부 OpenAI/Claude API에 의존하지 않는다.

- 실제 GPU에서 오픈소스 생성 모델을 vLLM으로 실행하고 문서 업로드부터 근거 기반 스트리밍까지 연결한다.
- 장애·취소·리소스 소유권·조직 격리를 재현 가능한 테스트로 검증한다.
- 기준 부하 측정 → 병목 발견 → 변경 → 동일 조건 재측정을 수행한다. 개선 여부, 품질과 자원 비용의 trade-off를 수치로 설명한다.
- 운영 환경에서 검증한 항목과 로컬에서만 검증한 항목을 구분한다. 이 명세 자체는 production 적합성이나 특정 성능을 보장하지 않는다.

기간은 4주, 하루 4~5시간 이상을 기준으로 한다. 주 5일이면 80~100시간이며 학습·환경 준비·실패 분석도 이 시간에 포함한다.

## 2. 범위

포함: FastAPI, 별도 vLLM, 단일 생성 모델·GPU, 한국어 중심 텍스트 PDF, 비동기 ingestion, PostgreSQL/pgvector, 단일 질문 RAG, 출처, SSE, API Key, 조직 격리, 장애 테스트, 지표와 부하 실험.

제외: OCR, 복잡한 표 구조 복원, 대화 기억, Agent/도구 실행, 회원가입·초대·관리자 UI, 문서별 ACL, 문서 버전 관리, 다중 모델 라우팅, Canary, 초기 양자화 비교, Kubernetes, Kafka, Elasticsearch, Microservices, 별도 분산 추적 인프라.

## 3. 구성과 경계

애플리케이션 실행 기준은 표준 CPython 3.14다(2026-09-10 확인한 패치: 3.14.7). 로컬·API·Worker·테스트 버전을 맞추고 전체 의존성 호환성은 초기 설치 시험에서 확인한다. vLLM·TEI는 독립 이미지의 지원 환경을 따르며 HTTP로 연결한다. 버전 선택과 업데이트 정책은 ADR-018에 기록한다.

배포는 일반 CPU 서버 한 대와 별도 원격 GPU를 기준으로 한다. CPU 서버에는 API·문서 Worker·작업 복구·PostgreSQL/pgvector·Redis와 원본 파일 볼륨을 둔다. GPU에는 vLLM과 생성 모델을 둔다. 로컬은 코드 작성과 GPU 없는 테스트에 사용한다. 예산은 4주 최대 10만 원(지출 목표 6~8만 원)으로 합의했다. 업체는 첫 단계의 검증 과제로 두며 보호된 연결의 우선 검토안은 보완 명세에 기록한다. 일반 서버는 Docker Compose를 사용하고, GPU 배포는 업체의 가상머신·관리형 컨테이너 지원에 맞춘다. 단일 서버 구성의 장애 시 중단 가능성을 명시한다.

```text
Client → FastAPI → inference client → vLLM → LLM / GPU
             │
             ├→ PostgreSQL + pgvector
             └→ Redis → Celery Worker → parsing / chunking / embedding
                                      └→ PostgreSQL + pgvector
```

FastAPI와 Worker는 같은 코드베이스의 별도 프로세스다. 질문 스트리밍은 작업 브로커를 통하지 않는다. 도메인 후보는 `users`, `documents`, `rag`, `inference`, `core`이며 최종 디렉터리 구조는 구현 계획에서 정한다.

의존 방향은 router → service → repository/client → infrastructure다. router에서 DB·vLLM 직접 접근을 피한다. 필요한 경계만 추상화하고, catch-all utils·God Service·service locator·순환 의존을 만들지 않는다. 명확한 타입과 명시적 의존성, context manager 기반 자원 관리, sync/async 경계를 유지한다.

임베딩은 일반 CPU 서버의 별도 TEI(Text Embeddings Inference) 컨테이너에서 실행한다. 초기 모델은 `intfloat/multilingual-e5-small`이다. API와 Worker는 내부 HTTP로 호출하고 웹 API 프로세스에 모델을 직접 로드하지 않는다. 문서와 질문은 같은 모델 버전·토크나이저·정규화 설정으로 384차원 벡터를 사용한다. 문서에는 `passage: `, 질문에는 `query: ` 접두어를 정확히 한 번 붙인다. 접두어·특수 토큰까지 512토큰 안에 들어가야 한다. 긴 질문을 조용히 잘라내지 않고 입력 오류로 반환한다. 모델 변경 시 기존 벡터와 섞지 않고 재색인한다.

TEI는 별도 프로세스지만 API·Worker·DB와 CPU·메모리를 공유한다. 문서 임베딩의 배치·동시성을 제한하고 질문 지연에 미치는 영향을 측정한다. 정확한 자원 제한과 이미지·모델 revision은 서버 선정과 호환성 검증 후 고정한다. 현재 모델 실행·한국어 품질·성능은 검증 전이다.

초기 생성 모델은 `Qwen/Qwen3-4B-Instruct-2507`이며 원격 NVIDIA GPU 하나에서 vLLM으로 실행한다. VRAM 24GB급을 장비 검토 기준으로 삼고 BF16으로 시작한다. 양자화·모델 자동 fallback은 제외한다. 업체·장비 조합의 실제 기동과 메모리 여유는 검증 전이다. 이미지 digest와 모델·토크나이저 revision은 초기 실행 검증 후 고정하고 실험 기록에 포함한다.

## 4. 인증과 데이터 접근

사전 생성한 사용자·조직에 사용자별 API Key를 발급한다. 원문은 발급 시만 제공하고 검증용 해시를 저장한다. 사용자와 조직은 인증 결과에서 결정하며 요청의 임의 조직 ID를 신뢰하지 않는다.

같은 조직의 사용자는 문서 목록·내용·처리 상태를 공유하고 질문할 수 있다. 삭제는 업로더만 가능하다. 다른 조직의 문서는 ID를 알아도 접근할 수 없어야 한다. 벡터 검색은 조직·처리 완료·삭제 여부 조건을 적용한 집합에서 Top-K를 구한다. Worker에도 동일한 조직·문서 연결 검증이 필요하다.

## 5. API 계약

| API | 계약 |
|---|---|
| POST /documents | 파일을 저장하고 작업을 등록한 뒤 202와 문서 ID 반환 |
| GET /documents | 인증된 조직의 삭제되지 않은 문서 목록 반환 |
| GET /documents/{id} | 접근 가능한 문서의 상태와 안전한 실패 사유 반환 |
| DELETE /documents/{id} | 업로더 확인 후 삭제 상태로 전환하고 검색에서 즉시 제외 |
| POST /questions | 단일 질문을 받아 조직 내 ready 문서 검색 후 SSE 반환 |

정확한 JSON 필드, 페이지네이션, 오류 코드와 추가 제한값은 [API와 운영 규칙](2026-09-10-llm-serving-lab-contracts.md)에 작성하고 2026-09-10 사용자 승인을 받았다.

## 6. 문서 처리와 삭제

원본은 API와 Worker가 같은 호스트에서 공유하는 Docker 영속 볼륨에 저장한다. 서버가 만든 조직 ID·문서 ID로 경로를 정하고, 원래 파일명은 표시용으로만 사용한다. 저장 공간을 웹에 직접 공개하지 않는다. 영속 볼륨은 백업을 대신하지 않는다.

pypdf로 페이지별 글자를 추출한다. 암호가 필요하거나 손상되었거나 유효 텍스트를 얻지 못한 PDF는 실패 사유를 구분한다. E5 토크나이저 기준 청크 본문은 최대 300토큰이고 이전 청크 끝부분 최대 40토큰을 같은 페이지에서 겹친다. 겹친 부분도 300토큰에 포함한다. 문단·문장 경계를 우선하고 긴 문장은 문자 경계를 보존하며 분할한다. 청크마다 새로운 본문을 포함해 진행하고 접두어·특수 토큰을 포함한 512토큰 한도를 다시 검사한다. 초기에는 페이지를 가로질러 합치거나 겹치지 않고 각 청크에 1부터 시작하는 PDF 물리적 페이지 번호를 기록한다. 300/40은 초기 설정이며 한국어 추출 순서와 페이지 경계의 문맥 손실을 평가해 조정한다.

파일 크기 외 페이지 수·추출량·처리 시간·Worker 메모리 사용도 제한한다. 등록에 실패한 임시 업로드 파일은 정리한다.

업로드 → 파일 저장 → DB 문서·작업 등록 → 작업 전달 → parsing → chunking → embedding → indexing 순서다. HTTP 요청 안에서 대형 PDF 처리나 embedding을 수행하지 않는다.

기본 상태는 `queued → processing → ready`다. 일시적 실패는 제한적으로 재시도하고 영구 실패 또는 소진 시 `failed`로 기록한다. 공개 실패 사유에 내부 경로·credential·문서 내용이 포함되지 않도록 한다.

PostgreSQL이 상태의 기준이다. 원본 저장 후 문서와 작업 기록을 하나의 DB 트랜잭션으로 등록하면 접수가 완료된다. 그 뒤 Redis로 알린다. 같은 코드베이스의 주기적 복구 프로세스가 미전달·기한 경과 작업을 재등록한다. Redis 장애 중에도 저장 용량과 대기 작업 수 한도 안에서는 접수할 수 있다.

Worker는 DB에서 만료 시간이 있는 처리 권한과 시도 번호를 원자적으로 얻고 실행 중 갱신한다. 만료 후에는 새 시도가 이어받을 수 있다. 현재 시도와 삭제 상태를 확인한 뒤 청크 저장과 ready 전환을 하나의 트랜잭션으로 확정하고 중복 방지 제약을 둔다. 파싱·임베딩 중에는 DB 트랜잭션을 열어두지 않는다. 늦게 복귀한 오래된 Worker의 결과는 반영하지 않는다.

일시적 장애는 간격을 늘려 제한적으로 재시도하고 입력 문제는 재시도하지 않는다. 초기에는 제한된 크기의 문서를 처음부터 재처리한다. 계산 자체의 중복은 가능하지만 결과의 중복 저장과 오래된 결과 공개를 막는다. 완료된 작업 알림을 다시 받아도 결과를 추가 저장하지 않는다. 구체적인 갱신 주기·만료 시간·재시도 횟수는 승인된 보완 명세를 따른다.

삭제는 먼저 `deleted` 상태로 전환한다. 삭제 반영 후 시작하는 새 조회·검색은 해당 문서를 제외한다. 검색은 짧은 DB 작업으로 수행하고 DB 스냅샷을 경계로 한다. 삭제 전 스냅샷에서 권한을 확인해 가져온 근거로는 진행 중 답변을 완료할 수 있다. 아직 검색하지 않은 대기 중 질문은 삭제된 문서를 사용하지 않는다. 삭제가 기존 답변의 즉각적인 중단이나 이미 전달된 내용의 회수를 의미하지 않는다.

물리 파일·청크 정리는 재시도 가능한 별도 작업으로 수행하고 실패를 관측한다. 이미 실행 중인 Worker가 삭제된 문서를 ready로 되살리거나 청크를 다시 노출해서는 안 된다. 진행 중 요청 메모리와 vLLM에 이미 전달한 입력의 즉시 소거는 보장하지 않는다. 즉각적인 접근 철회 요구가 생기면 진행 중 요청 추적·취소 정책을 재검토한다.

## 7. 검색과 답변 스트리밍

질문 embedding → 권한이 적용된 similarity search → Top-K → prompt 구성 → vLLM HTTP stream → SSE 순서다. 검색 결과가 없으면 추론을 생략하고 근거를 찾지 못했다고 반환한다. 결과가 있어도 답을 뒷받침하지 못하는 경우를 평가한다.

정규화한 384차원 벡터에 cosine distance 기반 정확 검색을 사용하고, 조직·ready·삭제·임베딩 버전 조건을 적용한 결과에서 최대 5개를 선택한다. 거리가 같으면 문서 ID·청크 순서로 정렬한다. 일반 DB 인덱스는 사용하되 HNSW 등 근사 검색은 초기 기준선에서 제외한다. 정확 검색이 정답 근거 검색 100%를 뜻하지는 않는다.

생성 모델 토크나이저로 지시문·질문·근거·출처 형식과 출력 예약량까지 계산한다. 입력 예산을 넘으면 관련도가 낮은 청크부터 제외한다. SSE sources에는 실제 모델에 전달한 근거 후보만 포함한다. 모델별 토큰 수가 같다고 가정하지 않는다. 유사도는 정답 확률로 표시하지 않으며 검증되지 않은 점수 컷오프를 추가하지 않는다.

전체 문맥 상한은 4096토큰, 출력 상한은 512토큰, chat template와 특수 토큰을 포함한 입력 상한은 3584토큰이다. 사용자는 질문만 전달하고 모델·system prompt·sampling·max_tokens·n을 덮어쓰지 못한다. 응답 개수는 1, temperature는 0으로 시작하고 도구 실행은 비활성화한다. temperature=0으로도 사실성이나 동일 출력의 절대적인 재현성을 보장하지 않는다.

질문은 E5 입력 한도와 생성 입력 한도를 각각 검사하고 초과 시 입력 오류를 반환한다. 검색 결과가 있지만 한 개도 생성 입력 예산에 넣지 못하면 context_budget_exceeded로 실패 처리하며 근거 없는 답변을 생성하지 않는다. 출력 한도에 도달한 종료는 done의 이유 length, 정상적인 모델 종료는 stop으로 구분한다. 잘린 답변을 자동으로 이어 생성하지 않고 잘림 비율을 기록한다.

| SSE 이벤트 | 의미 |
|---|---|
| sources | 근거 후보의 문서 ID·파일명·PDF 페이지 번호 |
| delta | 생성 텍스트 조각. 토큰 하나와 같다고 가정하지 않음 |
| done | 정상 완료와 종료 이유 |
| error | 응답 시작 이후 오류 코드 |

출처 후보가 있다는 사실만으로 답변의 사실성을 보장하지 않는다. 실제 답변과 근거의 일치를 평가한다. PDF 페이지는 책에 인쇄된 페이지 번호와 구분해야 한다.

인증·입력·과부하 오류는 SSE 시작 전에 HTTP 오류로 반환한다. 시작 이후는 error로 알리고 종료한다. 스트리밍 시작 후 자동 재시도하지 않는다. 클라이언트 disconnect 시 upstream 취소와 자원 정리를 수행하며 실제 vLLM 생성 중단 여부도 확인한다.

## 8. 안정성과 보안

초기 배포는 API 프로세스 하나로 제한한다. 질문 처리 자리는 임베딩·검색 전에 얻고 답변 종료와 자원 정리까지 유지한다. 실행 2개, 메모리 대기 4개, 대기 최대 10초로 시작한다. 대기 질문은 API 재시작 시 복구하지 않는다. 이는 Celery 문서 작업 대기열과 별개다. 여러 API 프로세스로 확장하기 전에는 전역 한도를 재설계한다.

upstream 연결 제한은 5초, upstream 본문 데이터 무응답 제한은 30초, 실행 자리 획득 후 전체 처리 제한은 120초다. 대기 10초는 별도로 측정한다. 클라이언트에 한 번의 쓰기가 막힌 시간은 최대 10초로 둔다. 이는 최초 개발 설정이며 실측 후 조정한다. 사용자별 요청 횟수 초과는 429, 전역 자리 부족·대기 만료는 SSE 시작 전 503으로 반환한다. SSE 시작 뒤 실패는 error로 종료하되 연결 종료·전송 정체 시 이벤트 전달은 보장하지 않고 자원을 정리한다.

upstream 읽기와 클라이언트 쓰기 사이에 무제한 큐를 만들지 않는다. 파싱 버퍼·이벤트 크기에도 제한을 둔다. 보호 설정을 고정한 과부하 시험과 동시 실행 한도를 변경하는 GPU 용량 실험을 구분한다.

- 요청과 upstream timeout, 동시 실행 제한, 제한된 대기, 과부하 거절을 둔다.
- 느린 소비자에 대해 무제한 버퍼링하지 않는다. 연결·대기·종료 조건을 명시한다.
- graceful shutdown, health/readiness와 자원 정리를 설계·검증한다.
- API Key별 rate limit, 파일·질문·prompt·출력 토큰 크기 제한을 설계한다. 추가 숫자와 집계 범위는 승인된 보완 명세를 따른다.
- vLLM은 내부 통신으로 제한한다. 외부 공개 인증 없는 추론 endpoint를 두지 않는다.
- Key·credential·민감한 prompt와 문서 내용을 로그에 남기지 않는다.
- 문서는 신뢰할 수 없는 입력이다. 지시문과 근거를 구분하되 prompt만으로 injection 방어를 보장하지 않는다. 검색 단계 권한과 도구 실행 제외가 보안 경계다.
- 모델 fallback은 MVP에서 제외한다. Circuit breaker는 실제 장애 패턴을 근거로 도입 여부를 판단한다.

## 9. 테스트와 평가

단위 테스트와 모의 HTTP 테스트는 GPU·실제 vLLM을 요구하지 않는다. 정상 응답, timeout, 연결 실패, malformed response, upstream 5xx, 중간 disconnect, 취소, 느린 소비자와 정리를 검증한다.

통합 테스트는 PostgreSQL/pgvector·Redis·Worker의 실제 상호작용을 검증한다. 재시도·중복 전달·삭제와 처리의 경합·DB/브로커 전달 실패·조직 격리를 포함한다.

실제 GPU 검증에서는 모델 로드·HTTP 호환성·토큰 스트리밍·취소·성능을 확인한다. 모의 서버 처리량은 LLM 성능으로 보고하지 않는다.

직접 작성한 가상 사내 규정 PDF와 질문 20개로 초기 한국어 평가를 수행한다. 직접 질문 10개·표현 변경 6개·답 없는 질문 4개를 개발용과 고정 검증용 각 10개에 5/3/2개씩 배정한다. 정답 내용·문서·페이지·근거 문장을 기록하고 청크 ID에 정답을 종속시키지 않는다. 정답 있는 질문의 Hit@5, 실제 prompt에 전달한 근거의 적합성, 답변 사실·출처 일치, 답 없는 질문의 거절을 따로 기록한다. 한글·문단 추출도 확인한다. 검증용 문제로 반복 튜닝했다면 독립 평가라고 부르지 않고 새 문제를 추가한다. 작은 세트의 결과를 일반적인 한국어 성능으로 과장하지 않는다.

## 10. 관측성과 실험

관측 항목: HTTP 요청 수·오류율·P50/P95/P99, TTFT, input/output tokens, token throughput, 대기 시간·길이, retrieval/embedding latency, 문서 작업 상태, GPU utilization·VRAM.

Prometheus/Grafana 기반 기본 대시보드를 계획하되 지표별 수집원과 정의는 승인된 보완 명세를 따른다. 특히 앱에서 관측한 첫 텍스트 도착 시간과 모델 측 TTFT, 앱 대기와 vLLM 대기를 구분한다. API Key·prompt·사용자별 값처럼 민감하거나 cardinality가 큰 값을 지표 label로 사용하지 않는다.

동시성 1/10/50/100을 단계적으로 실험한다. 모델·GPU·서빙 설정·데이터셋·입력/출력 길이 조건·워밍업·실행 시간·캐시 조건을 기록한다. 부하 발생기가 병목이 아닌지도 확인한다. 성공 요청 지연과 함께 오류율·거절률·실제 처리량을 기록한다. 구체적인 SLO는 최초 측정 후 결정한다.

## 11. 4주 검증 단계

1. 1주차: FastAPI와 inference 경계, SSE, Docker, 실제 GPU/vLLM 초기 연동, 기본 측정.
2. 2주차: PDF ingestion, 작업 복구, pgvector 검색과 근거 기반 답변 연결.
3. 3주차: 장애·취소·보안 검증 강화, 자원 제한과 대시보드.
4. 4주차: 기준 부하 실험, 병목 개선과 재측정, README·배포 재현 절차·결과 정리.

권한과 측정 지점은 해당 기능 구현 시부터 포함한다. 각 단계는 별도 검증 가능한 구현 묶음으로 계획하고 TDD로 진행한다.
