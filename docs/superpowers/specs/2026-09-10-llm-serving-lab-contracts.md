# API와 운영 규칙 — 최종 설계 검토안

날짜: 2026-09-10. 상태: **사용자 검토·승인 완료 — 구현 전**.

[전체 설계](2026-09-09-llm-serving-lab-design.md)를 보완한다. 이미 합의한 구조를 바꾸는 문서가 아니라, 구현자가 다르게 해석할 수 있는 빈칸을 채우는 문서다. 아래 수치는 승인된 초기 기본값이며 성능 측정 결과가 아니다. 실제 환경에서 바꾸면 이유와 변경 전후 값을 기록한다.

## 먼저 쉽게 읽기

- 문서를 올리면 접수증을 받고, 처리 결과는 나중에 확인한다.
- 질문이 몰리면 정해진 수만 기다리게 하고 나머지에는 잠시 후 다시 요청해 달라고 알린다.
- 작업자가 멈추면 다른 작업자가 이어받는다. 뒤늦게 돌아온 작업자가 예전 결과를 덮어쓰지는 못한다.
- GPU는 필요할 때 빌린다. 껐다는 생각만 하지 않고 실제 요금이 멈췄는지 확인한다.
- 속도는 빠른 요청만 골라 보여주지 않는다. 실패하거나 거절된 요청도 함께 기록한다.

## 1. 접수증과 오류 형식

인증은 `Authorization: Bearer <API Key>`로 전달한다. API Key는 URL에 넣지 않는다. 응답에는 서버가 만든 `request_id`를 포함하고, `X-Request-ID` 헤더로도 제공한다. 시간은 UTC ISO 8601, ID는 UUID 문자열이다. 알 수 없는 요청 필드는 거절한다.

| 요청 | 성공 응답 |
|---|---|
| `POST /documents` | multipart의 `file` 하나. 202와 `document_id`, `status: queued`, `created_at`, `request_id`. Location은 상태 조회 주소 |
| `GET /documents` | 200과 `items`, `next_cursor`, `request_id`. 각 항목은 `document_id`, `filename`, `status`, `created_at`, `updated_at` |
| `GET /documents/{id}` | 200과 목록 항목 필드, `failure`(실패 시 안전한 code/message, 나머지 null), `request_id` |
| `DELETE /documents/{id}` | 논리 삭제 완료 후 204. 응답 본문 없음 |
| `POST /questions` | JSON `{"question":"휴가 신청은 어떻게 하나요?"}`. 성공 시 SSE |

목록은 `limit` 기본 20, 최대 100이며 `(created_at, document_id)` 내림차순 커서 방식이다. 커서는 검증하고 항상 현재 사용자의 조직 조건을 별도로 적용한다. 여러 페이지를 조회하는 동안 목록 전체의 고정 스냅샷을 보장하지 않는다.

다른 조직·존재하지 않음·삭제된 문서의 조회는 404다. 같은 조직에서 타인이 올린 문서 삭제는 403이다. 삭제 기록이 남아 있는 동안 업로더의 반복 삭제는 204이며, 타 조직에는 항상 404다. 삭제 기록은 MVP 기간 동안 유지한다. 원본 다운로드 API는 추가하지 않는다.

일반 오류 본문은 `{"error":{"code":"...","message":"..."},"request_id":"..."}`다. 내부 예외·경로·upstream 응답 원문은 반환하지 않는다.

| HTTP | 적용 |
|---|---|
| 401 / 403 / 404 | 인증 실패 / 허용되지 않은 작업 / 접근 가능한 문서 없음 |
| 413 / 415 / 422 | 업로드 또는 요청 바이트 한도 초과 / 지원하지 않는 파일 형식 / 질문·커서·토큰 한도 등 입력 오류 |
| 429 | 사용자별 요청 속도 초과. Retry-After 제공 |
| 503 | 처리 자리·작업 접수 한도·저장 여유 부족, 필수 의존 서비스 연결 불가, 종료 중 |
| 502 / 504 | upstream 비정상 응답 / 처리 시간 초과 |

PDF 내부 손상·암호화·페이지/추출량 제한 초과는 접수 이후 Worker가 발견할 수 있다. 이 경우 이전 202가 취소되는 것이 아니라 문서 상태가 `failed`가 된다. 접수 성공은 문서 분석 성공을 뜻하지 않는다.

## 2. 답변 스트림

각 SSE 이벤트의 data는 JSON이며 `request_id`를 포함한다. 다음 예의 출처는 실제 prompt에 포함한 후보이고 정답 보증이 아니다.

```text
event: sources
data: {"request_id":"...","sources":[{"source_id":"S1","document_id":"...","filename":"휴가규정.pdf","page":2}]}

event: delta
data: {"request_id":"...","text":"휴가는 "}

event: done
data: {"request_id":"...","finish_reason":"stop","usage":{"input_tokens":900,"output_tokens":80}}

```

`sources`는 한 번, `delta`는 0회 이상, 마지막에는 `done` 또는 `error` 하나만 보낸다. 실패 이벤트는 `code`, `message`를 담는다. 연결이 끊기거나 전송이 막히면 마지막 이벤트 전달을 보장하지 못한다. 클라이언트는 종결 이벤트 없는 종료를 불완전한 답변으로 표시한다.

검색 결과가 없으면 sources는 빈 배열, delta는 정해진 한국어 안내문, done 이유는 `no_context`이고 usage는 null이다. 모델을 호출한 완료 이유는 `stop` 또는 `length`다. 모델이 토큰 사용량을 제공하지 않으면 usage는 null로 두고 0으로 꾸미지 않는다. 출력 중 정상 종료 신호 없이 upstream이 닫히면 오류로 처리한다.

인증·검증·검색과 upstream 상태 확인 중 알려진 실패는 SSE 시작 전에 HTTP 오류로 반환한다. 스트림 시작 후에는 상태 코드를 바꾸지 않고 error로 종료한다. 질문의 자동 재시도와 이어받기는 MVP에서 제외한다.

## 3. 작은 환경을 위한 제한

이미 합의한 질문 실행 2개·대기 4개·대기 10초, 연결 5초·upstream 무응답 30초·실행 120초·한 번의 전송 정체 10초는 유지한다.

| 추가 초기 기본값 | 범위와 의도 |
|---|---|
| PDF 20 MiB, 요청 전체 21 MiB | 파일과 multipart 부가 정보를 구분. Content-Length를 신뢰하지 않고 실제 수신량 제한 |
| PDF 100페이지, 추출 문자 100만, 청크 5,000개 | 문서 하나 기준. 먼저 닿은 한도 적용 |
| 질문 JSON 16 KiB | 토큰 검사 전 요청 크기 제한. E5 512/생성 입력 3584 토큰 검사는 별도 유지 |
| upstream SSE 이벤트 64 KiB, 미완성 파싱 버퍼 128 KiB | 무제한 누적 방지. 초과 시 upstream 오류로 중단 |
| 사용자별 질문 분당 20회, 업로드 3회, 나머지 합계 60회 | 단일 API 프로세스에서 사용자·범주별 sliding window로 제한 |
| 조직별 미완료 작업 10개, 전체 100개 | queued·processing 합계. DB 트랜잭션에서 동시 접수까지 직렬화해 검사 |
| 파일 볼륨 최소 여유 1 GiB | 수신 바이트 제한과 함께 검사. 디스크 부족 예외도 처리하며 부분 파일 정리 |
| 문서 Worker 실행 1개, 임베딩 배치 최대 16청크 | API·DB와의 CPU/메모리 경쟁을 줄이는 출발점 |

속도 제한 상태는 메모리에 두므로 API 재시작 시 초기화된다. Redis 장애 중에도 제한된 문서 접수가 가능해야 하므로 이 제한을 Redis에 의존시키지 않는다. 사용자 수는 사전 생성된 소수 계정으로 제한하고 오래된 기록은 제거한다. 대규모 공개 가입·다중 API 프로세스 확장 시 이 방식을 재설계한다.

파싱 프로세스에는 컨테이너 메모리 한도와 작업 시간 한도를 함께 둔다. 구체적인 메모리 값은 CPU 호스트 선정 후 기동 시험에서 고정한다. 파일 크기만으로 압축된 PDF의 메모리 폭증을 막을 수 있다고 가정하지 않는다. 공개 데모는 제한된 접근자에게 제공하며 인터넷 규모의 공격 방어를 입증한 것으로 표현하지 않는다.

## 4. 작업 중단과 복구

DB 작업 기록은 `attempt_id`, `attempt_count`, `lease_until`, `next_attempt_at`을 가진다. 처리 권한은 120초, 갱신은 20초, 복구 스캔은 30초 주기로 시작한다. 시간 판단은 DB 시간을 기준으로 한다. 한 시도의 절대 실행 상한은 300초다. 갱신이 계속되어도 무한 실행하지 못한다.

최대 3회 실행(최초 포함)하며 일시적 실패 뒤에는 10초, 30초를 기다린다. PDF 입력 오류는 재시도하지 않는다. 프로세스 종료·메모리 초과는 권한 만료 후 재시도 대상으로 처리하되 총 횟수를 넘으면 failed가 된다. 시도 횟수는 실제 DB claim에서 증가하고 중복 메시지 수로 증가하지 않는다.

Celery의 전달·재전달은 DB claim을 거쳐야 하며 별도의 무제한 자동 재시도와 겹치지 않게 한다. 처리 중 DB 갱신을 못하면 결과 공개를 중단한다. 결과 확정 시 현재 시도·미삭제·유효한 권한을 다시 확인한다. 복구와 삭제 청소는 같은 코드베이스의 작은 주기 작업으로 유지하고 범용 워크플로 엔진을 만들지 않는다.

파일 삭제 실패도 재시도·지표로 남긴다. DB에 등록되지 않은 임시 파일은 생성 후 1시간이 지났고 활성 업로드가 아닌 경우 정리한다. 파일을 먼저 저장하고 DB 등록하기 전 프로세스가 죽는 상황도 포함한다.

## 5. 배포·보안·종료

일반 서버는 Compose, GPU는 업체가 지원하는 이미지 배포 방식을 사용한다. CPU↔GPU 연결의 우선 검증 후보는 SSH 터널이다. GPU 추론 포트는 loopback에만 바인딩하고, CPU의 터널 입구도 공개하지 않는다. 전용 키·호스트 키 검증·최소 접근 권한을 사용한다.

이것은 **선정 조건**이지 특정 업체에서 이미 검증된 구성이라는 뜻이 아니다. 대여 전 해당 환경이 TCP 포워딩 가능한 SSH와 필요한 접근 제한을 지원하는지 확인하고, 짧은 실험으로 통신·터널 중단·재연결·취소를 검증한다. 지원하지 않으면 다른 배포 후보를 검토한다. 보호되지 않은 공개 vLLM 주소로 우회하지 않는다.

외부 API 앞에는 HTTPS 프록시를 두고 SSE 버퍼링·전송 시간 제한을 실제 스트림 시험으로 확인한다. DB·Redis·TEI·관리 지표는 외부 공개하지 않는다. 비밀값은 저장소와 이미지에 넣지 않는다. 로그에는 질문·문서·Authorization을 남기지 않고 request_id·처리 단계·시간·안전한 오류 코드를 기록한다.

문서에 “이전 지시를 무시하라”가 있어도 신뢰할 수 있는 지시로 취급하지 않도록 prompt에서 근거와 지시를 구분한다. 그러나 이것만으로 prompt injection을 해결했다고 주장하지 않는다. 조직 검색 제한과 도구 실행 금지가 실제 보안 경계이며 공격 문서로도 평가한다.

`/health/live`는 프로세스 응답, `/health/ready`는 종료 중 여부·DB 연결·파일 저장 가능 여부를 확인한다. GPU가 꺼졌다는 이유로 문서 API 전체를 비준비 상태로 만들지 않는다. 질문은 필요한 TEI/vLLM 연결 불가 시 503, Redis 중단 시 문서 접수는 기존 한도 안에서 유지한다. 의존 서비스별 상태는 내부 관측 대상으로 분리한다.

종료 신호를 받으면 새 요청을 거절하고 최대 30초 동안 진행 요청을 마친 뒤 취소·정리한다. 프로세스 강제 종료까지 추가 10초 여유를 둔다. Worker를 종료해도 DB 작업 기록이 남아 복구되어야 한다. 재배포 전에는 접수·Worker를 멈춘 상태에서 DB와 PDF를 함께 백업하고, 별도 보호된 위치에 보관한다. 적어도 한 번 새 볼륨으로 복원해 문서 검색까지 확인한다. 단일 호스트이므로 무중단·고가용성을 보장하지 않는다.

## 6. 무엇을 측정할지

| 측정값 | 정의와 수집 위치 |
|---|---|
| HTTP 요청·오류·거절·완료 지연 | API에서 수집. SSE는 헤더 반환 시간이 아닌 스트림 종료까지 측정 |
| 사용자가 기다린 첫 글자 시간 | 부하 도구에서 요청 시작부터 첫 비어 있지 않은 delta까지. sources는 첫 글자가 아님 |
| 모델 TTFT·실행/대기 요청·모델 대기 시간 | vLLM 지표. 외부 첫 글자 시간과 다른 이름으로 보관 |
| 입력/출력 토큰·초당 출력 토큰 | vLLM 지표 또는 usage. SSE 조각 개수를 토큰 수로 사용하지 않음 |
| 앱 대기·검색·임베딩 시간 | 각각 별도 API 지표. Worker 임베딩도 질문과 구분 |
| 작업 실패·시도·정체·정리 실패 | DB 상태와 작업 계측 |
| GPU 사용률·VRAM | 대여 환경의 NVIDIA 지표 수집 수단 확인 후 기록. 수집 불가를 0으로 표시하지 않음 |

Prometheus와 Grafana로 위 지표를 모은다. 이미지 버전별 실제 지표 이름·단위를 초기 연동 때 확인해 매핑한다. request_id·문서명·사용자 ID는 metric label에 넣지 않는다. GPU 수집 수단과 정확한 이미지 digest·모델 revision은 기동 시험 결과로 배포 기록에 고정한다.

부하 도구는 Python 경험을 활용하는 **Locust**를 사용한다. POST SSE를 끝까지 읽고 종결 이벤트·중간 실패·첫 글자를 별도로 계측한다. GPU 없는 모의 서버로 부하 스크립트의 정확성을 먼저 검증한다.

각 동시성 1/10/50/100에서 워밍업 후 기본 5분씩 3회 측정한다. 표본 수가 적으면 P99를 안정적인 수치로 해석하지 않고 표본 수도 공개한다. 실제 종료 시간은 마지막 요청 정리 시간을 포함한다. 실패율·거절률·완료 건수·토큰 처리량·GPU 지표를 함께 남긴다. 모델·입출력 길이·문서·캐시·부하 발생기·배포 지역을 기록하고 개선 전후 같은 조건을 유지한다.

앱의 보호 한도(실행 2/대기 4)를 유지한 시험과, 격리된 실험 환경에서 실행 한도를 바꾸는 GPU 용량 시험을 분리한다. 개선 목표 숫자는 첫 측정 후 설정한다. 더 빠르게 만들지 못했더라도 병목 근거와 실패한 개선 가설을 기록한다.

## 7. 비용과 4주 완료 기준

**합의: 4주 총 상한 10만 원, 지출 목표 6~8만 원.** GPU 4.5만·CPU 3만·저장소 등 1만·예비비 1.5만 원으로 배분한다. 상세 계산은 [비용 문서](../../cloud-options.md)를 따른다. 연장 기간 비용은 별도다.

합의한 운영 규칙: 매 실험 전후 사용 내역과 남은 고정 비용을 확인한다. 예상 총액 7만 원에서 남은 실험을 재배분하고 9만 원에서 새 GPU 실험을 보류한다. 아직 청구되지 않은 비용까지 합산한다. 이는 자동 과금 차단 기능이 아니다. 서버·저장소 해제 여부를 각각 확인한다.

4주 완료의 최소 증거는 실제 GPU RAG 시연, 조직 격리 테스트, 스트림 취소·upstream 실패 테스트, 작업 중단 복구, 기본 대시보드, 병목 개선 시도와 재측정 보고서다. 시간이 부족하면 UI 꾸미기·대시보드 세부 패널·추가 모델 실험을 줄인다. 조직 격리와 자원 제한을 생략하거나 모의 측정을 GPU 실측으로 바꾸어 표현하지 않는다.

구현 계획은 ① 스트리밍+실제 GPU 첫 연동 ② 문서 처리와 RAG ③ 운영 검증 ④ 성능 실험으로 나누고 각 단계의 실패 테스트부터 작성한다. 업체 선정·실제 자원 용량·버전 고정은 첫 단계의 검증 과제다. 배포 호환성과 전체 예상 비용이 맞지 않으면 그 사실을 기록하고 배포안을 조정한다.
