# 처음 읽는 분을 위한 llm-serving-lab

## 무엇을 만드나요?

**회사 문서를 읽고 질문에 답하는 AI 서비스**를 만듭니다.

예를 들어 직원이 출장 규정 PDF를 올린 뒤 “출장 숙박비는 얼마까지 지원되나요?”라고 물으면, 서비스가 관련 내용을 찾아 답하고 어느 문서의 몇 페이지를 참고했는지 보여줍니다.

문서에 근거가 없으면 근거를 찾지 못했다고 알려주는 것을 목표로 합니다. 다만 AI는 근거가 있어도 잘못 답할 수 있으므로, 답변과 출처가 맞는지 따로 확인합니다.

## 왜 만드나요?

개발자는 이미 Python으로 웹 서비스, 데이터베이스, 배포를 다뤄본 경험이 있습니다. 이제 **AI 모델을 직접 실행하고, 사람들이 안정적으로 사용할 수 있게 운영하는 능력**을 기르려 합니다.

중요한 질문은 다음과 같습니다.

- 한 사람이 물을 때와 여러 사람이 동시에 물을 때 속도가 얼마나 달라질까요?
- 답변이 너무 늦거나 AI 서버가 멈추면 어떻게 처리할까요?
- 사용자가 창을 닫았는데 AI가 계속 답을 만들며 자원을 쓰고 있지는 않을까요?
- A 회사 직원에게 B 회사 문서가 보이지 않게 하려면 어떻게 해야 할까요?
- 속도가 느려졌을 때, 어디가 문제인지 숫자로 찾아낼 수 있을까요?

이 질문을 직접 시험하고 해결한 기록이 포트폴리오의 핵심입니다. 아직 얻지 않은 성능 개선 결과를 미리 약속하지는 않습니다.

## 어떻게 동작하나요?

도서관에서 자료를 찾아 설명해주는 일을 떠올리면 이해하기 쉽습니다. 아래는 이해를 위한 비유이며, 실제 AI의 답변 정확성을 보장하는 설명은 아닙니다.

### 문서를 준비할 때

1. **문서를 받습니다.** 사용자가 PDF를 올립니다.
2. **글자를 꺼냅니다.** PDF에서 읽을 수 있는 텍스트를 추출합니다.
3. **작게 나눕니다.** 긴 문서를 검색하기 좋은 크기로 나눕니다.
4. **찾기 위한 숫자 정보를 만듭니다.** 글의 관련성을 비교할 수 있게 숫자 묶음으로 바꿉니다.
5. **보관합니다.** 글 조각, 페이지 정보, 숫자 정보를 데이터베이스에 저장합니다.

큰 문서를 처리하는 동안 업로드 화면을 계속 기다리게 하지 않습니다. 먼저 접수 번호에 해당하는 문서 ID를 돌려주고, 별도 작업자가 처리합니다. 사용자는 그 번호로 진행 상태를 확인합니다.

### 질문할 때

1. **누가 질문하는지 확인합니다.** 사용자와 소속 회사를 확인합니다.
2. **볼 수 있는 문서에서 찾습니다.** 질문과 관련 있는 글 조각을 고릅니다.
3. **AI에 질문과 근거를 전달합니다.** 선택한 글을 바탕으로 답하게 합니다.
4. **답변을 조금씩 보여줍니다.** 전체 답변이 완성되기 전부터 생성된 내용을 전달합니다.
5. **출처를 보여줍니다.** 사용자가 원래 문서를 확인할 수 있게 합니다.

다른 회사 문서는 처음부터 검색 대상에 들어가면 안 됩니다. AI에게 “비밀을 말하지 마”라고 부탁하는 것만으로 보안을 맡기지 않습니다.

## 어떤 프로그램이 어떤 일을 맡나요?

| 이름 | 쉬운 설명 | 이 프로젝트에서 하는 일 |
|---|---|---|
| FastAPI | 요청을 받는 안내 창구를 만드는 도구 | 사용자 확인, 업로드 접수, 질문과 답변 전달 |
| 생성 모델 | 입력을 바탕으로 답변을 만드는 AI | 문서 근거를 받아 답변 생성 |
| vLLM | AI 모델을 실행하고 요청을 처리하는 서버 프로그램 | 모델을 메모리에 올리고 답변 생성 요청 처리 |
| TEI | 검색용 모델을 실행하고 요청을 처리하는 서버 프로그램 | 일반 서버의 CPU에서 질문과 문서를 검색용 숫자로 변환 |
| GPU | 많은 계산을 병렬로 처리하는 장치 | AI 계산 실행 |
| PostgreSQL | 정보를 보관하고 찾아주는 데이터베이스 | 사용자·문서·처리 상태·글 조각 저장 |
| pgvector | PostgreSQL에서 숫자 묶음의 유사성을 검색하는 확장 기능 | 질문과 관련 있는 글 조각 검색 |
| Celery Worker | 시간이 걸리는 일을 맡는 별도 작업 프로그램 | PDF 읽기, 나누기, 검색 정보 만들기 |
| Redis | 이 프로젝트에서는 처리할 작업을 전달하는 저장소 | API에서 Worker로 문서 작업 전달 |
| Prometheus / Grafana | 상태를 숫자로 모으고 화면으로 보여주는 도구 | 요청 수, 지연, 오류, GPU 사용 상태 확인 |

웹 요청을 받는 프로그램과 AI를 실행하는 프로그램은 분리합니다. AI는 GPU와 큰 메모리가 필요해 일반 웹 요청 처리와 자원 요구가 다르기 때문입니다.

## 처음에는 어디까지 만드나요?

- 한국어 중심으로, 글자를 선택할 수 있는 PDF만 받습니다. 사진처럼 스캔된 PDF의 글자 인식은 제외합니다.
- 같은 회사 사람들은 문서를 함께 볼 수 있고, 올린 사람만 삭제할 수 있습니다.
- 질문 하나씩 답합니다. 이전 대화를 기억하는 기능은 나중으로 미룹니다.
- AI 모델 하나와 GPU 한 대로 시작합니다.
- 평소에는 로컬에서 개발하고 실제 AI 검증과 속도 실험 때만 GPU를 빌리는 방향입니다. 구체적인 대여 환경과 예산은 아직 정하지 않았습니다.

## 잘 만들었는지 어떻게 확인하나요?

**동작, 안전, 성능을 나누어 확인합니다.**

- 동작: 문서를 올리고 답변과 출처를 받을 수 있는지 확인합니다.
- 안전: 다른 회사 문서를 못 보는지, AI 서버가 멈추거나 사용자가 나가도 요청 자원이 제대로 정리되는지 확인합니다.
- 성능: 동시 요청을 늘려 어디서 느려지는지 측정하고, 변경 전후를 같은 조건으로 비교합니다.

예를 들어 “동시 요청 10개에서 첫 답변이 늦어졌다 → 대기 위치를 찾았다 → 대기 처리 방식을 바꿨다 → 같은 질문으로 다시 측정했다”처럼 기록합니다. 이것은 기록 방식의 예시이며, 실제로 얻은 결과는 아닙니다.

## 문서에서 나오는 어려운 말

| 용어 | 뜻 |
|---|---|
| LLM | 많은 텍스트를 학습해 문장을 생성하는 대규모 언어 모델 |
| Serving, 서빙 | 모델을 실행해 두고 요청을 받아 결과를 돌려주는 일 |
| Inference, 추론 | 모델이 입력을 받아 결과를 계산하는 과정 |
| RAG | 질문과 관련된 자료를 먼저 찾고, 그 자료를 AI에 함께 주어 답하게 하는 방식 |
| Embedding, 임베딩 | 텍스트의 관련성을 비교하는 데 사용할 숫자 묶음으로 바꾸는 것 |
| Chunk, 청크 | 긴 문서를 나눈 작은 글 조각 |
| Token, 토큰 | 모델이 텍스트를 처리하는 단위. 한 글자나 한 단어와 항상 같지는 않음 |
| Streaming / SSE | 서버가 답변을 한 번에 모아서 보내지 않고 조금씩 전달하는 방식 / 그때 사용하는 전송 형식 |
| Tenant, 테넌트 | 서로 데이터를 구분해야 하는 고객 단위. 이 프로젝트에서는 조직 |
| API Key | 요청한 사용자를 확인하는 비밀 키. 비밀번호처럼 보호해야 함 |
| Modular Monolith | 코드를 역할별로 나누되 여러 독립 서비스로 쪼개지 않고 운영하는 구조 |
| Retry, 재시도 | 실패한 일을 다시 실행하는 것. 모든 실패를 무조건 다시 시도하지는 않음 |
| Idempotency, 멱등성 | 같은 작업이 중복 실행되어도 중복 저장 등 원치 않는 결과가 생기지 않도록 하는 성질 |
| Backpressure | 받는 쪽이 느릴 때 데이터를 무한히 쌓지 않도록 생산·전달 속도를 제어하는 것 |
| Rate limit | 일정 시간에 받을 수 있는 요청 수를 제한하는 것 |
| Concurrency limit | 동시에 처리할 수 있는 요청 수를 제한하는 것 |
| TTFT | 요청 후 첫 토큰이 오기까지 걸리는 시간. 어디서 재는지 함께 명시해야 함 |
| P95 latency | 측정한 요청 중 약 95%가 그 시간 이내에 끝났다는 지연 지표. 평균과 다름 |
| Throughput | 일정 시간에 처리한 양. 요청 수인지 토큰 수인지 단위를 함께 적음 |
| Observability | 기록과 지표를 통해 시스템 안에서 무슨 일이 일어나는지 파악할 수 있게 하는 것 |
| Prompt Injection | 문서나 질문 속의 지시가 AI가 따라야 할 원래 지시를 바꾸려는 문제 |
| MVP | 핵심 목표를 검증할 수 있도록 처음 만드는 최소 범위 |
| ADR | 어떤 설계 방법을 왜 선택했는지 남기는 의사결정 기록 |
| TDD | 기대 동작을 확인하는 테스트를 먼저 쓰고, 통과하도록 구현하는 개발 방식 |

더 구체적인 결정 이유는 [의사결정 기록](decisions/README.md), 개발 기준은 [설계 명세](superpowers/specs/2026-09-09-llm-serving-lab-design.md)에서 확인할 수 있습니다.
