# 개발 환경 확인 기록

확인일: 2026-09-09

## 확인한 사실

`nvidia-smi --query-gpu=name,memory.total --format=csv,noheader` 결과:

```text
NVIDIA GeForce RTX 3080, 10240 MiB
```

GPU 메모리 용량은 10GiB다. 모델을 실행하고 테스트한 결과는 아니다. 현재 사용 가능한 여유 메모리, Linux 환경 GPU 접근, 선택한 vLLM 이미지의 호환성도 아직 검증하지 않았다.

Windows 시스템 정보 조회는 접근 거부로 CPU·시스템 RAM을 확인하지 못했다. `wsl --list --verbose`도 E_ACCESSDENIED로 종료되어 WSL 설치 여부나 배포판 상태를 판단할 수 없다. 설치되지 않았다는 뜻으로 해석하지 않는다.

## 로컬 GPU 검토 이력

기존에는 로컬 GPU 정보가 없어 GPU 단기 대여를 기본으로 논의했다. GPU 확인 후 로컬 실행 우선을 제안했지만 사용자는 실무 배포 경험을 위해 로컬 GPU 이외의 방법을 요청했다. 따라서 로컬 GPU 우선안을 기본 배포 방향으로 채택하지 않는다. 기존 비용 결정 ADR-001의 원격 GPU 단기 대여 방향을 이어서 검토한다.

Qwen3-1.7B는 로컬 GPU 검토 중 조사했던 후보이며 채택하지 않았다. 이후 ADR-015에서 원격 배포의 초기 생성 모델을 Qwen3-4B-Instruct-2507로 합의했다. 한국어 품질·메모리·속도는 미검증이며 모델 다운로드나 실행은 수행하지 않았다.

## 원격 배포 검토 방향

사용자가 원하는 경험은 직접 원격 서버에 배포하고 운영하는 것이다. 개발 컴퓨터는 코드 작성·GPU 없는 테스트에 사용하고, 실제 생성 모델은 원격 GPU에서 실행하는 구성을 검토한다. 로컬 개발과 운영 배포는 서로 다른 역할이다.

- GPU 가상머신: 원격 Linux 서버에서 Docker·vLLM·포트 접근·저장소·재시작을 직접 관리하는 후보다.
- 관리형 GPU 컨테이너: 이미지로 배포하고 호스트 관리는 업체에 맡기는 후보다. 일반 가상머신과 다르므로 Docker Compose 전체 구성을 그대로 실행할 수 있다고 가정하지 않는다.
- 서버리스 GPU: 요청에 맞춰 실행 자원이 시작되는 방식이다. 시작 대기와 플랫폼의 확장 정책을 별도로 고려해야 한다.

ADR-012에서 일반 CPU 서버 한 대와 원격 GPU 한 개로 배포하는 방향을 합의했다. GPU의 생성 모델은 Qwen3-4B-Instruct-2507, CPU TEI의 임베딩 모델은 multilingual-e5-small이다. 업체·최종 요금·실행 시간·서버 지역·네트워크 연결 방식은 아직 미선정이다. 로컬 장비 사용 여부 자체가 production 적합성을 결정하지는 않으며, 실제 실험 환경과 운영 수준을 구분해 기록한다.

## 실무 적합성 검토

검토일: 2026-09-09. 아래는 공식 문서와 프로젝트 목표를 대조한 설계 판단이다. 특정 방식의 업계 사용 비율이나 취업 효과를 입증한 조사는 아니다.

**결론:** 직접 LLM을 배포·운영하고 장애와 성능을 설명하려는 이 프로젝트에는 원격 GPU에서 vLLM을 직접 운영하고 검증하는 방향이 적합하다. 원격에 배포했다는 사실만으로 production 수준이 되는 것은 아니다.

**근거:** AWS는 서버리스·관리형·직접 관리형 추론을 구분하고, 직접 관리형은 인프라와 소프트웨어를 제어하려는 요구에 적합하다고 설명한다. vLLM은 외부 노출 endpoint 제한과 reverse proxy 보호를 권고하며, 첫 토큰 지연·대기 시간·실행/대기 요청 수 등의 운영 지표를 제공한다. 따라서 직접 설정하고 장애·지표를 관찰하려는 학습 목표와 연결된다. 모든 조직에 직접 관리가 더 낫다는 의미는 아니다.

**포트폴리오에서 검증할 내용:**

- 이미지와 모델 버전을 고정하고 새 원격 환경에 배포를 재현한다.
- 모델 준비가 끝난 뒤 요청을 받고, 재시작과 이전 버전 재배포 절차를 확인한다. 자동 Canary는 기존 범위대로 제외한다.
- 외부 사용자는 애플리케이션을 통해 접근하고 vLLM의 추론·관리·지표 endpoint는 필요한 내부 주체로 접근을 제한한다.
- GPU 서버 종료·네트워크 단절·과부하 시 백엔드의 timeout·취소·거절 동작을 확인한다.
- 사용자 관점의 응답 시간과 vLLM 내부 지표를 함께 측정해 네트워크 지연과 모델 대기를 구분한다.
- GPU를 해제한 뒤 남는 저장소 등 비용과 재배포 시 데이터 복구 절차를 기록한다.

**4주 범위에 대한 권고:** 일반 CPU 서버 한 대에 API·Worker·PostgreSQL/pgvector·Redis를 두고 GPU 서버 한 대에 vLLM을 배치하는 구성을 우선 검토한다. API와 문서 Worker가 같은 호스트의 파일 볼륨을 공유한다는 기존 설계와 양립한다. 두 서버의 접근 제한·통신 경로를 설계해야 한다. 실제 업체는 가격·GPU 확보 가능성·네트워크·영속 저장소 조건을 확인한 뒤 고른다.

**한계:** 단일 CPU 서버와 GPU 서버는 각각 장애 시 서비스가 중단될 수 있는 지점이다. 이 구성은 실무 운영 문제를 검증하는 소규모 환경이며 고가용성을 보장하지 않는다. GPU 단기 대여는 포트폴리오 비용 절감 수단이고 24시간 서비스 운영 실적은 아니다. 관리형 서비스는 운영 부담을 줄이는 유효한 선택이며, 이번에는 직접 제어하는 학습 목표 때문에 우선순위를 낮춘다.
