# 의사결정 기록 (ADR)

ADR은 **어떤 문제 때문에, 어떤 방법을, 왜 골랐는지 남기는 기록**입니다. 나중에 방향이 바뀌어도 당시의 이유를 이해할 수 있도록 작성합니다. 기술 용어가 낯설다면 [처음 읽는 분을 위한 설명](../introduction.md)을 먼저 읽어주세요.

## 결정만 쉽게 읽기

| 기록 | 우리가 고른 방법 | 고른 이유 | 감수할 점 |
|---|---|---|---|
| 001 | 평소에는 내 컴퓨터에서 개발하고, 실제 AI 실험 때 GPU 대여 | 비용을 줄이면서 직접 운영 경험 확보 | 실험 환경을 준비하는 시간이 필요 |
| 002 | 웹 프로그램은 하나의 프로젝트로 만들고, AI 실행 서버는 별도로 둠 | 복잡도를 줄이고 GPU가 필요한 부분을 분리 | 처음부터 모든 부분을 따로 배포하지는 못함 |
| 003 | 큰 문서는 별도 작업자가 처리 | 사용자가 업로드 화면에서 오래 기다리지 않게 함 | 중복 실행과 중간 실패의 복구가 필요 |
| 004 | 한국어 텍스트 PDF부터 시작 | 문서 읽기 기능보다 AI 서빙 검증에 집중 | 스캔 문서와 복잡한 표는 지원하지 않음 |
| 005 | 같은 회사끼리 문서를 공유하고, 올린 사람만 삭제 | 작은 범위로 실제 접근 권한을 검증 | 같은 회사 안의 개인 비공개 문서는 지원하지 않음 |
| 006 | 답변을 조금씩 전달하고, 중간 실패는 알린 뒤 종료 | 빨리 읽기 시작하게 하고 중복 답변 방지 | 끊긴 답변을 자동으로 이어받지는 못함 |
| 007 | 모델 하나로 먼저 측정하고 병목 개선 | 4주 안에 설명할 수 있는 실험 결과 확보 | 여러 모델과 GPU 비교는 나중에 진행 |
| 008 | 원본은 비공개 저장 공간에 두고 페이지별 글을 작게 나눔 | 간단하게 시작하면서 출처를 확인하기 쉽게 함 | 서버 분리 시 저장 방식을 바꿔야 하고 페이지 경계에서 문맥이 끊길 수 있음 |

아래 각 기록의 **재검토 조건**은 “어떤 상황이 되면 이 결정을 바꿀지”를 뜻합니다.

기록일: 2026-09-09

상태 `합의`는 대화에서 승인된 방향을 의미하며, 구현이나 성능 검증이 완료되었다는 뜻이 아닙니다. 대안은 선택 이유를 설명하기 위한 비교이고 실제 실험 결과가 아닙니다.

## ADR-001 — 프로젝트 목적과 비용 운영

**상태:** 합의

**배경:** 기존 Python 백엔드 경험을 AI Backend / LLM Serving으로 확장한다. LLM 서빙 경험은 처음이며, 포트폴리오 비용을 최소화한다. 하루 4~5시간 이상 투자할 수 있다.

**결정:** 이름은 `llm-serving-lab`으로 한다. 평소에는 로컬에서 개발하고, 실제 연동과 성능 측정 시 GPU를 단기간 대여하는 방향을 기본으로 한다. 1주차에 실제 vLLM 연동을 검증한다. 상시 공개 서비스보다 재현 절차·실행 영상·실험 결과를 우선한다.

**대안:** GPU 구매, 상시 GPU 서버 운영, 외부 상용 LLM API 의존.

**이유와 제약:** 지속적인 GPU 비용을 줄이면서 실제 서빙 경험을 확보한다. 모의 서버로 GPU 성능을 검증할 수 없으며, 대여 환경 준비와 모델 다운로드에도 시간이 든다. GPU 사용료 외 저장소 등 잔여 비용도 확인해야 한다. 당시 구체적인 예산 상한과 업체는 미선정이었다. 예산은 이후 ADR-016으로 확정했다.

**재검토 조건:** 반복 대여 비용과 준비 시간이 커지거나 상시 시연 요구가 생긴 경우.

## ADR-002 — Modular Monolith와 별도 추론 서버

**상태:** 합의

**결정:** FastAPI Modular Monolith에서 시작한다. `router → service → repository/client → infrastructure` 방향을 유지하고, 실제 모델은 별도 vLLM 서버에서 실행한다. FastAPI 내부의 `inference` 모듈이 통신 경계를 담당한다. 웹 프로세스에서 생성 모델을 로드하지 않는다.

**대안:** Django와 FastAPI 동시 도입, 독립 Inference Gateway, 초기 Microservices.

**이유와 제약:** async HTTP와 SSE를 경험하면서 배포·통신 지점을 제한한다. 추론은 GPU·VRAM 등 자원 요구가 달라 별도 서버가 필요하다. 애플리케이션 내부 모듈은 독립 배포되지 않는다.

**재검토 조건:** 추론 계층의 독립 확장·배포·장애 격리 요구가 발생한 경우 Gateway 분리를 검토한다. 복잡한 사용자·과금·관리 도메인이 실제로 생길 때 Django를 재검토한다.

## ADR-003 — 문서 작업에 Celery와 Redis 사용

**상태:** 합의

**결정:** 문서 처리에 Celery + Redis와 별도 Worker를 사용한다. API와 Worker는 같은 코드베이스를 사용한다. PostgreSQL이 문서·작업 상태의 기준이며, Redis는 작업 전달 브로커 역할을 한다. 질문 스트리밍은 Celery를 통하지 않는다.

**대안:** PostgreSQL 작업 테이블을 직접 폴링하는 Worker, HTTP 요청 안에서 처리.

**이유와 제약:** 작업 실행과 재시도 도구를 활용해 LLM 서빙에 시간을 배정한다. Redis 운영과 Celery 학습 비용이 추가된다. Celery만으로 DB/브로커 간 원자성, 중복 실행, 중단 후 복구가 해결되지는 않는다. 미전달·정체 작업 재등록과 멱등 처리가 필요하다.

**재검토 조건:** 실제 운영 부담이 이점을 초과하거나 작업 전달량·복구 요구가 달라진 경우. 단순히 기술을 추가하려는 이유로 Kafka를 도입하지 않는다.

## ADR-004 — 한국어 텍스트 PDF와 pgvector

**상태:** 합의

**결정:** 한국어 문서·질문·답변을 중심으로 하고 기술 문서의 영어 용어도 다룬다. 입력은 텍스트 선택이 가능한 PDF로 한정한다. PostgreSQL + pgvector를 사용한다. 단일 질문과 출처 표시에 집중하며 대화 이력은 제외한다.

**대안:** OCR·표 복원 포함, 전용 Vector DB, 멀티턴 대화.

**이유와 제약:** 파싱과 제품 기능의 범위를 제한하고 기존 DB 경험을 활용한다. 텍스트 선택이 가능해도 추출 순서와 한글 품질은 보장되지 않아 검증이 필요하다. 생성 모델과 임베딩 모델은 한국어 평가로 선정해야 한다.

**재검토 조건:** 실제 문서에서 OCR·표 이해가 필수이거나 측정 결과 pgvector가 요구를 충족하지 못하는 경우.

## ADR-005 — API Key와 조직 공유 권한

**상태:** 합의

**결정:** 사전 생성한 사용자·조직과 사용자별 API Key로 시작한다. Key 원문은 발급 시만 제공하고 서버에는 검증용 해시를 저장한다. 같은 조직은 문서 조회·질문을 공유하며 삭제는 업로더만 허용한다. 조직 ID는 인증 결과로 결정한다. 가입·초대·관리자 UI와 문서별 공유 설정은 제외한다.

**대안:** 전체 계정 관리 기능, 업로더 전용 문서, 문서별 ACL.

**이유와 제약:** 작은 인증 범위로 실제 리소스 소유권과 테넌트 격리를 검증한다. 같은 조직의 모든 사용자가 문서를 볼 수 있다는 제품 제약이 있다. 키 발급·폐기와 보관은 운영 절차가 필요하다.

**검증:** 타 조직 문서 ID 직접 조회, 상태 조회, 삭제 시도와 검색 결과·답변 근거 누출을 테스트한다. 검색은 권한 조건이 적용된 문서 집합에서 Top-K를 구한다.

**재검토 조건:** 조직 내 비공개 문서, 관리자 권한, 사용자 이동·온보딩 요구가 생기는 경우.

## ADR-006 — SSE 및 실패 처리 계약

**상태:** 합의

**결정:** `POST /questions`에서 SSE를 반환한다. 이벤트는 `sources`, `delta`, `done`, `error`로 제한한다. SSE 시작 전 실패는 HTTP 오류로, 시작 후 실패는 `error`로 알린다. 스트리밍 시작 후 자동 재시도하지 않는다. 연결 종료 시 upstream 연결과 자원을 정리한다.

**대안:** 전체 답변을 모아서 반환, WebSocket, 중간 실패 시 자동 재생성.

**이유와 제약:** 단방향 답변 전송에 집중하고 중복 응답을 피한다. HTTP 응답 시작 후 상태 코드를 바꿀 수 없다. 클라이언트는 POST 응답 스트림을 읽을 수 있어야 한다. 텍스트 조각 하나를 모델 토큰 하나로 간주하지 않는다.

**검증:** timeout, 연결 실패, upstream 5xx, malformed 응답, 중간 disconnect, 취소, 느린 소비자를 검증한다. 실제 GPU 통합 테스트에서 vLLM의 생성 중단 여부도 확인한다.

**재검토 조건:** 양방향 실시간 통신이나 재연결·이어받기가 제품 요구로 생기는 경우.

## ADR-007 — 제한된 운영 범위와 측정 우선

**상태:** 합의

**결정:** 모델 하나·GPU 한 대에서 시작하고 병목 하나 이상의 개선 전후를 같은 조건으로 측정한다. 동시성 1/10/50/100은 실험 조건이며 처리 성공을 보장하는 목표가 아니다. timeout, 동시 실행 제한, 제한된 대기, 과부하 거절, 취소와 종료 시 자원 정리를 설계한다. 모델 fallback·Canary·양자화 비교·분산 추적 인프라는 후속 범위로 둔다.

**대안:** 초기부터 여러 모델·GPU 비교, 무제한 요청 대기, 기술 스택 확장.

**이유와 제약:** 4주 안에 설계 이유와 실측 근거를 남긴다. 좋은 지연 수치만 제시하면 과부하 거절 효과와 실제 처리량을 혼동하므로 오류율·거절률도 함께 기록한다. 성공적인 성능 개선 수치는 아직 없으며, 개선 실패와 품질 저하도 기록 대상이다.

**재검토 조건:** 기준 측정에서 발견된 병목이나 장애가 추가 기법의 필요성을 뒷받침하는 경우. Circuit breaker도 장애 패턴을 확인하고 도입 여부를 판단한다.

## ADR-008 — 원본 PDF 보관과 글 나누기

**상태:** 합의

**쉽게 설명하면:** 원본은 잠긴 서류함에 보관하고, 검색할 때는 작은 메모로 나누어 사용한다. 메모마다 원본의 페이지 번호를 붙인다.

**결정:** 초기에는 API와 Worker가 같은 호스트의 Docker 영속 볼륨을 공유한다. 원본 파일 경로는 서버가 만든 조직 ID·문서 ID로 구성하고 업로드 파일명은 표시용 정보로만 저장한다. 볼륨을 웹 정적 파일 경로로 공개하지 않는다. 원본 접근이 필요한 기능을 추가할 때도 API의 권한 검사를 거친다.

**글 추출:** pypdf로 페이지별 텍스트를 추출한다. 암호가 필요한 PDF, 손상된 PDF, 유효 텍스트를 추출하지 못한 PDF는 이유를 구분해 실패 처리한다. OCR은 수행하지 않는다. 업로드 확장자와 MIME만 믿지 않고 실제 파싱 결과도 확인한다. 파일 크기만으로 파싱 자원 소모가 제한되지는 않으므로 페이지·추출량·작업 시간과 Worker 메모리에도 제한이 필요하다.

**글 나누기:** 페이지 정보를 보존하면서 문단을 우선해 나눈다. 너무 긴 문단은 임베딩 모델의 입력 한도 안으로 다시 나누고, 경계의 문맥을 보존하도록 일부 텍스트를 겹친다. 청크에 PDF의 1부터 시작하는 물리적 페이지 번호를 기록한다. 초기에는 페이지를 가로질러 합치지 않는다. 정확한 청크 크기와 겹침 크기는 임베딩 모델 선정 시 정하고 한국어 평가로 확인한다.

**대안:** 처음부터 S3 계열 저장소 사용, 복잡한 문서 레이아웃 분석기, 페이지 전체를 하나의 청크로 사용.

**이유와 제약:** 저장소 서비스를 추가하지 않고 출처를 추적하기 쉽게 시작한다. API와 Worker를 다른 호스트로 분리하면 공유 볼륨만으로는 부족하다. 단순 추출은 글 순서가 틀릴 수 있으며, 페이지 경계에서 문맥이 끊길 수 있다. 영속 볼륨 자체는 백업이 아니다.

**삭제·실패 처리:** 삭제 상태를 먼저 저장하고 원본과 청크는 재시도 가능한 정리 작업으로 제거한다. DB 등록에 실패한 임시 업로드도 정리한다. 삭제 전에 근거를 확보한 진행 중 답변까지 중단할지는 별도 계약으로 확정한다.

**검증:** 한글 추출·페이지 번호·긴 문단 분할·잘못된 PDF·권한 없는 파일 접근·Worker 재시작 후 원본 접근을 확인한다. 청크 크기 제한에는 임베딩 모델의 지시문과 특수 토큰도 고려한다.

**재검토 조건:** 한국어 평가에서 추출 순서나 페이지 경계가 검색 실패의 주원인이 되거나, API/Worker가 서로 다른 호스트에서 실행되어야 하는 경우.

**참고:** [pypdf 텍스트 추출 설명](https://github.com/py-pdf/pypdf/blob/main/docs/user/extract-text.md). 라이브러리 기능에 대한 참고이며 한국어 문서 품질을 검증한 결과는 아니다.

## ADR-009 — 작업 전달 실패와 중복 실행 복구

**상태:** 합의

**쉽게 설명하면:** 접수 장부를 먼저 쓰고 작업자에게 알린다. 알림이 사라지면 장부를 보고 다시 보낸다. 같은 접수 번호가 두 번 전달되어도 결과는 한 번만 등록한다.

**결정:** 원본 저장 후 문서와 작업 기록을 하나의 DB 트랜잭션으로 등록한다. 이 등록이 완료되면 접수는 성공한 것으로 간주한다. 작업 알림은 그 이후 Redis로 전달한다. 같은 코드베이스의 주기적 복구 프로세스가 미전달 작업과 기한이 지난 작업을 찾아 재등록한다. Redis 장애 중에도 접수는 가능하되 저장 용량과 대기 작업 수 제한을 넘으면 새 접수를 거절한다.

**작업 선점:** Worker는 DB에서 원자적으로 처리 권한과 시도 번호를 얻은 후 실행한다. 처리 권한에는 만료 시간이 있고 실행 중 갱신한다. 중복 메시지를 받은 다른 Worker는 유효한 권한이 있으면 처리하지 않는다. 중단 후 권한이 만료되면 새 시도가 이어받을 수 있다.

**결과 확정:** 초기에는 제한된 크기의 문서를 한 작업 단위로 재처리한다. 시도별 결과를 준비하고 현재 시도 번호·문서 삭제 여부를 확인한 뒤 청크 저장과 ready 전환을 한 트랜잭션에서 확정한다. 추론·파싱·임베딩을 하는 동안 DB 트랜잭션을 열어두지 않는다. 청크 식별자에 중복 방지 제약을 둔다. 오래된 Worker가 뒤늦게 끝나도 새 시도 결과를 덮어쓰지 못한다.

**재시도:** 일시적인 연결 장애 등은 간격을 늘려 제한적으로 재시도한다. 손상·암호 필요·텍스트 없음 등 입력 문제는 재시도하지 않는다. 최대 시도 횟수와 시간 간격은 자원 제한 설계에서 확정한다. 완료된 작업 메시지가 다시 와도 아무것도 저장하지 않는다.

**대안:** 메시지 전달 성공만 믿기, 실패 때마다 수동 재업로드, 정확히 한 번 실행된다고 가정하기.

**이유와 제약:** DB와 Redis 사이의 전달 실패를 복구하고 결과의 중복 저장을 막는다. 대신 작업 기록·만료·복구 프로세스가 필요하다. 장애 시 계산 자체가 중복될 수 있으며, 보장하려는 것은 계산이 딱 한 번 실행되는 것이 아니라 잘못된 중복 결과가 공개되지 않는 것이다. 큰 문서를 단계별로 이어서 처리하는 기능은 초기 범위에서 제외한다.

**검증:** DB 등록 직후 프로세스 종료, Redis 전달 실패, 전달 후 확인 기록 실패, Worker 강제 종료, 중복 메시지, 권한 만료 후 오래된 Worker 복귀, 삭제와 완료의 경합을 재현한다.

**재검토 조건:** 전체 문서 재처리 비용이 실제 병목이 되거나, 작업 규모가 주기적 복구의 처리 한계를 넘는 경우.

## ADR-010 — 문서 삭제와 진행 중인 답변

**상태:** 합의

**쉽게 설명하면:** 서가에서 책을 치우면 이후에는 그 책을 새로 꺼낼 수 없다. 다만 치우기 전에 내용을 받아 설명을 시작한 사람의 설명까지 중단시키지는 않는다. 이는 이해를 위한 비유이며 데이터의 완전한 회수를 뜻하지 않는다.

**결정:** 삭제 상태가 DB에 반영된 뒤 새로 시작하는 조회·검색은 해당 문서를 제외한다. 검색은 짧은 DB 작업으로 수행한다. 그보다 앞선 검색 스냅샷에서 권한을 확인하고 근거를 가져온 질문은 답변을 끝낼 수 있다. 질문 접수 시간이나 첫 답변 도착 시간이 아니라 검색의 DB 스냅샷을 기준으로 경계를 정한다. 삭제 시 모든 진행 중 질문을 찾아 취소하는 기능은 MVP에서 제외한다.

**예시:** 질문이 근거를 가져옴 → 업로더가 삭제함 → 기존 답변은 계속될 수 있음 → 삭제 반영 후 새 검색에서는 해당 문서를 찾을 수 없음. 대기 중 질문도 아직 검색하지 않았다면 삭제된 문서를 사용하지 않는다.

**대안:** 삭제 시 해당 문서를 참조하는 모든 답변 취소, 답변이 끝날 때까지 삭제 대기.

**이유와 제약:** 삭제와 검색 사이에 테스트 가능한 경계를 두고, 진행 중 질문과 문서 사이의 별도 추적·취소 기능을 추가하지 않는다. 대신 삭제 완료 후에도 기존 답변에 문서 내용과 출처 후보가 전달될 수 있다. 이미 전달된 내용은 회수할 수 없다. 즉각적인 접근 철회가 필요한 서비스에는 이 정책이 충분하지 않다.

**물리 정리:** 원본과 DB 청크는 재시도 가능한 정리 작업으로 제거한다. 진행 중 요청의 메모리와 vLLM에 이미 전달한 입력까지 즉시 지운다는 보장은 하지 않는다. 정리 실패는 관측하고 재시도한다.

**검증:** 검색 전 삭제, 근거 확보 후 삭제, 대기 중 삭제, 문서 처리 중 삭제를 각각 재현한다. 삭제 이후 새 검색에서 제외되고 Worker가 문서를 되살리지 않는지 확인한다.

**재검토 조건:** 진행 중인 내용 전달도 즉시 중단해야 하는 보안 요구나 사용자·조직 권한의 실시간 철회 요구가 생기는 경우.

## ADR-011 — 질문 처리의 동시 실행과 대기 제한

**상태:** 합의

**쉽게 설명하면:** 식당에 테이블과 대기석을 정한다. 둘 다 차면 손님을 끝없이 줄 세우지 않고 나중에 다시 와달라고 안내한다. 한 손님이 너무 오래 자리를 차지하는 것도 제한한다.

**결정:** 최초 개발 설정은 API 프로세스 하나를 기준으로 질문 실행 2개, 대기 4개, 대기 최대 10초로 시작한다. 실행 자리는 질문 임베딩·검색 전에 얻고 답변 종료와 자원 정리까지 유지한다. 입력 검증과 인증은 그 전에 수행한다. 대기는 메모리에서 관리하며 Redis/Celery 문서 작업 대기열과 별개다. API 재시작 시 대기 중 질문은 복구하지 않는다.

**초기 시간 설정:** upstream 연결은 최대 5초, upstream 응답 본문 데이터가 오지 않는 시간은 최대 30초, 질문 실행 자리를 얻은 시점부터 전체 처리 시간은 최대 120초로 둔다. 대기 10초는 전체 실행 120초와 별도로 측정한다. 클라이언트 전송이 막힌 한 번의 쓰기 대기는 최대 10초로 제한한다. 이는 최적값이나 서비스 수준 약속이 아니라 실패 동작을 개발·시험하기 위한 시작값이다.

**초과 동작:** 사용자별 요청 횟수 초과는 429, 전역 실행·대기 자리가 모두 찼거나 대기 시간이 만료되면 SSE 시작 전 503으로 응답한다. SSE 시작 뒤 timeout은 error로 종료한다. 연결이 이미 끊겼거나 쓰기가 막혔다면 오류 이벤트의 전달을 보장하지 않고 연결 종료·upstream 취소·자원 정리를 수행한다.

**느린 소비자:** upstream을 읽는 속도가 클라이언트 전송보다 무한히 앞서가지 않게 한다. 앱 내부에 무제한 텍스트 큐를 두지 않고, upstream 이벤트 크기와 파싱 버퍼에도 상한을 둔다. 실제 전송 정체 감지와 취소는 ASGI 서버를 사용하는 통합 테스트에서 확인한다.

**대안:** 무제한 대기, 대기 없이 즉시 거절, 처음부터 분산 동시성 제어.

**이유와 제약:** 과부하와 timeout을 작은 규모로 재현한다. API 프로세스별 제한이므로 프로세스를 여러 개 띄우면 전체 한도가 늘어난다. 초기 배포는 API 1개 프로세스로 명시하고 확장 전에 전역 한도 설계를 바꾼다. 동시 실행 2개는 GPU의 최대 처리 능력을 뜻하지 않는다.

**측정과 재검토:** 보호 설정을 고정한 과부하 테스트와 동시 실행 한도를 단계적으로 변경하는 GPU 용량 실험을 구분한다. 실행 2개 상태에서 부하 100개를 보낸 결과를 GPU 동시 처리 100개의 성능이라고 보고하지 않는다. 모델 로딩과 워밍업은 readiness 이전에 수행한다. 첫 실측 후 timeout·동시성·대기를 조정하고 설정별 결과를 남긴다.

**후속 설정:** 파일 크기, 사용자별 요청 횟수, prompt·출력 토큰, 이벤트 크기 등 나머지 제한은 별도 자원 설정에서 확정한다.

## ADR-012 — 소규모 원격 배포로 운영 검증

**상태:** 합의

**쉽게 설명하면:** 내 컴퓨터에서는 코드를 작성하고 시험한다. 실제 서비스를 확인할 때는 일반 업무용 서버와 AI 계산용 서버를 따로 빌려 연결한다.

**결정:** 일반 CPU 서버 한 대에 API·문서 Worker·작업 복구·PostgreSQL/pgvector·Redis를 두고, 별도 원격 GPU에 vLLM과 생성 모델을 배포하는 구조로 진행한다. 로컬 GPU는 프로젝트의 필수 실행 환경으로 사용하지 않는다. 애플리케이션은 Modular Monolith를 유지한다. 문서 Worker와 API의 공유 파일 볼륨은 일반 서버에 둔다.

**배포:** 이미지와 모델 버전을 고정해 재현한다. 일반 서버에서는 Docker Compose를 사용한다. GPU는 가상머신 또는 관리형 컨테이너 중 업체 특성에 맞게 이미지를 실행한다. Runpod Pod처럼 Compose를 지원하지 않는 환경에 전체 Compose 구성을 그대로 옮길 수 있다고 가정하지 않는다. 당시 업체·예산 상한·연결 보호의 구체적 방식은 미선정이었다. 이후 예산은 ADR-016으로 확정했고, 연결 보호는 보완 명세에 검토안을 작성했다. 업체 선정과 실제 연결 검증은 초기 배포 과제다.

**대안:** 로컬 GPU만으로 최종 검증, 모든 구성 요소를 하나의 GPU 서버에 배치, 처음부터 다중 서버 자동 확장.

**이유와 제약:** 원격 배포·추론 서버 장애·네트워크 지연·접근 제한·운영 지표를 직접 검증한다. 대신 두 서버 간 연결 관리와 비용이 생긴다. 서버가 각각 하나이므로 무중단 운영과 고가용성을 보장하지 않는다. GPU를 필요한 시간에 대여하는 방식은 실험용 비용 절감이며 상시 운영 실적은 아니다.

**검증:** 새 원격 환경 배포, 모델 준비 후 요청 수신, GPU 서버 종료 시 오류 처리, 내부 endpoint 접근 제한, 사용자 체감 지연과 vLLM 내부 지표 분리 측정.

**재검토 조건:** 실험 요구·예산·업체의 안전한 연결 지원이 이 구성을 충족하지 못하거나, 실제 부하가 이중화·독립 확장을 요구하는 경우.

**관련 기록:** [참조 구조 비교](../architecture-comparison.md), [업체별 비교](../cloud-options.md). ADR-001의 원격 GPU 대여 방향을 구체화한다.

## ADR-013 — CPU 임베딩 서버와 한국어 검색 기준 모델

**상태:** 합의

**쉽게 설명하면:** 자료를 찾기 위한 색인을 만드는 담당자와 답변을 쓰는 담당자를 구분한다. 색인 담당자는 일반 서버에서 일하고 답변 담당자는 GPU 서버에서 일한다.

**결정:** 일반 CPU 서버에 임베딩 전용 Docker 컨테이너를 하나 둔다. Hugging Face Text Embeddings Inference(TEI)를 사용하고 `intfloat/multilingual-e5-small`을 초기 검증 모델로 선택한다. FastAPI와 문서 Worker는 내부 HTTP로 호출한다. 생성 모델은 기존대로 별도 GPU의 vLLM에서 실행한다. 모델을 직접 로드하는 사용자 정의 웹 코드를 추가하지 않는다.

**선택 이유:** GPU 대여와 무관하게 문서 준비·검색을 검증하고, 웹 API 프로세스에 모델 메모리·계산을 넣지 않는다. 이미 만들어진 임베딩 서빙 도구를 사용해 자체 서빙 엔진 구현을 피한다. TEI는 CPU 이미지와 BERT 계열을 지원하고, E5-small은 다국어·384차원 모델이다. 실제 선택 버전에서의 실행 호환성과 한국어 품질·CPU 지연은 아직 검증하지 않았다.

**입력 계약:** 문서는 `passage: `, 질문은 `query: ` 접두어를 정확히 한 번 붙이고 모델 버전·토크나이저·정규화 설정을 일치시킨다. 모델의 512토큰 한도에 접두어와 특수 토큰도 포함한다. 긴 문서는 분할하고, 너무 긴 질문은 잘라서 검색하지 않고 입력 오류로 반환한다. DB에는 384차원 벡터와 임베딩 모델 식별·버전을 기록한다. 모델 변경 시 기존 벡터와 혼합하지 않고 재색인한다.

**대안:** API와 Worker에서 직접 모델 로드, GPU에서 별도 임베딩 모델 실행, 더 긴 입력을 받는 BGE-M3로 시작. BGE-M3는 공식 안내상 1024차원·8192토큰 입력을 지원하지만, 이번에는 작은 모델을 기준으로 품질과 비용을 먼저 측정한다. 어떤 모델이 한국어에서 더 낫다는 실측 결론은 아직 없다.

**자원 경합:** CPU·메모리를 API·DB와 공유하므로 컨테이너 자원과 문서 임베딩 배치·동시성을 제한한다. 문서 작업이 질문 검색을 늦추는지 함께 측정한다. 프로세스 분리만으로 CPU 병목이나 장애 격리가 완전히 해결되지는 않는다. 실제 제한값은 서버 사양에 맞춰 확정한다.

**검증:** TEI 기동·384차원 유한값 응답·입력 길이·접두어·timeout·잘못된 응답을 확인한다. 작은 한국어 평가 세트에서 근거가 상위 검색 결과에 포함되는지 측정한다. 단위 테스트에서는 실제 TEI를 요구하지 않고 CPU 통합 테스트에서 모델을 검증한다.

**재검토 조건:** 한국어 근거 검색 품질이나 질문 임베딩 지연이 기준을 충족하지 못하는 경우. 먼저 파싱·청킹·입력 형식 문제와 모델 자체 한계를 구분한 뒤 더 큰 모델·GPU·별도 CPU 호스트를 검토한다.

**출처:** [TEI 모델·하드웨어 지원](https://huggingface.co/docs/text-embeddings-inference/supported_models), [E5-small 모델 설명](https://huggingface.co/intfloat/multilingual-e5-small/blob/main/README.md), [BGE-M3 모델 설명](https://huggingface.co/BAAI/bge-m3).

## ADR-014 — 작은 검색 기준선과 한국어 평가

**상태:** 합의

**쉽게 설명하면:** 책을 작은 메모로 나누고 질문과 가까운 메모 다섯 장을 먼저 고른다. 정답이 적힌 메모를 잘 골랐는지와 AI가 그 메모를 제대로 읽었는지를 따로 채점한다.

**분할:** E5 토크나이저 기준 청크 본문 최대 300토큰, 같은 페이지 안에서 이전 청크의 끝부분 최대 40토큰을 다음 청크와 겹치게 한다. 겹친 부분도 300토큰 한도에 포함한다. 문단·문장 경계를 우선하고 긴 문장은 문자 경계를 보존하며 토큰 한도 안으로 분할한다. 매 청크는 새 본문을 포함해 앞으로 진행해야 한다. 페이지를 넘겨 겹치지 않는다. 실제 모델 입력은 접두어·특수 토큰까지 다시 검사하고 512토큰을 넘기지 않는다. 숫자는 초기 기준선이며 검증 후 조정할 설정이다.

**검색:** 정규화한 384차원 벡터에 cosine distance를 사용하고 pgvector의 정확 검색으로 시작한다. 조직·ready·삭제 여부·임베딩 버전 조건을 적용한 뒤 거리순으로 최대 5개를 고른다. 같은 거리에는 문서 ID와 청크 순서로 순서를 고정한다. 테넌트·상태·문서 연결을 위한 일반 DB 인덱스는 사용하며, 근사 벡터 인덱스인 HNSW는 초기 기준선에서 제외한다.

**전달:** 최대 5개를 생성 모델의 입력 예산 안에서 관련도 순서로 넣는다. 생성 모델의 토크나이저로 지시문·질문·출처 형식·출력 예약 공간까지 계산한다. E5의 300토큰이 생성 모델에서도 300토큰이라고 가정하지 않는다. 입력 예산을 넘으면 낮은 순위 청크부터 제외하고 SSE sources에는 실제 전달한 근거 후보만 넣는다. 모델의 정확한 입력 예산은 생성 모델 선정 때 고정한다.

**근거 없음:** 접근 가능한 검색 결과가 없으면 모델을 호출하지 않는다. 결과가 있다는 사실이나 유사도 점수만으로 정답 근거가 있다고 단정하지 않는다. 초기에는 근거로 답할 수 없으면 없다고 답하도록 구성하고 실제 결과를 평가한다. 유사도 점수를 확률이나 신뢰도로 표시하지 않는다. 점수 컷오프는 검증 자료 없이 임의로 추가하지 않는다.

**평가:** 직접 작성한 가상 사내 규정 PDF와 한국어 질문 20개로 시작한다. 직접 찾을 수 있는 질문 10개, 표현을 바꾼 질문 6개, 문서에 답이 없는 질문 4개다. 개발용 10개와 고정 검증용 10개에 각각 5/3/2개를 배정한다. 개발용으로 조정하고 고정 검증용은 최종 확인에 사용한다. 이를 반복해 튜닝했다면 더 이상 독립 검증이라고 부르지 않고 새 문제를 보충한다.

**채점:** 정답이 있는 질문에는 정답 내용·원본 문서·페이지·근거 문장을 기록한다. 청킹이 바뀌어도 정답이 유지되도록 청크 ID만 정답으로 삼지 않는다. 검색 상위 5개에 정답 근거가 하나 이상 포함되는 비율(Hit@5), 실제 prompt에 포함된 근거의 적합성, 답변의 사실 일치·출처 일치, 답 없는 질문의 거절 여부를 나눠 기록한다. 정확 벡터 검색은 모델이 만든 거리순 결과를 정확히 구한다는 뜻이며 정답 검색 100%를 뜻하지 않는다. 작은 평가 세트의 결과를 일반적인 한국어 성능으로 과장하지 않는다.

**보안 테스트:** 타 조직의 더 유사한 문서, 삭제 문서, 처리 중 문서, 다른 임베딩 버전이 검색되지 않는지는 품질 평가와 별개의 통합 테스트로 검증한다. 근거가 준비된 시점과 삭제 시점의 계약은 ADR-010을 따른다.

**대안:** 처음부터 큰 청크·많은 근거·HNSW·hybrid search·reranker를 모두 추가. 초기에는 원인을 구분할 수 있는 기준선을 우선한다.

**재검토 조건:** 한국어 근거 누락, 페이지 경계 손실, 입력 예산 초과 또는 검색 지연이 실제로 문제가 되는 경우. HNSW 등 변경 시 같은 질문과 데이터에서 검색 품질·지연을 함께 비교한다.

**출처:** [pgvector 정확 검색과 근사 인덱스](https://github.com/pgvector/pgvector). 구체적인 300/40/5와 평가 문제 수는 라이브러리 권장값이 아니라 이 프로젝트의 초기 설계 제안이다.

## ADR-015 — 단일 생성 모델과 제한된 토큰 예산

**상태:** 합의

**쉽게 설명하면:** 답변 담당자에게 작은 자료 묶음을 주고 짧게 답하도록 한다. 처음부터 책 전체를 읽히거나 긴 답변을 요구하지 않아 비용과 대기 시간을 관리하기 쉽게 만든다.

**결정:** `Qwen/Qwen3-4B-Instruct-2507`을 초기 생성 모델로 선택한다. 원격 NVIDIA GPU 한 개에서 vLLM으로 실행한다. 검토 기준 장비는 VRAM 24GB급이며 특정 업체·GPU를 구매하거나 이 용량에서 실행을 검증한 상태는 아니다. 더 큰 메모리 장비로도 같은 모델을 사용할 수 있다. BF16을 초기 형식으로 사용하고 양자화는 제외한다. 실제 드라이버·vLLM 이미지·모델 조합의 호환성은 초기 GPU 검증에서 확인한다.

**선택 이유:** 공식 모델은 4B 파라미터의 non-thinking Instruct 모델이며 vLLM 실행 안내가 있다. 별도 thinking 출력 경로 없이 문서 기반 답변을 만드는 기준 모델로 검증한다. 공개 벤치마크를 우리 한국어 문서 성능으로 간주하지 않는다. 이전 Qwen3-1.7B는 로컬 GPU 가능성을 검토하면서 조사했던 후보이며 원격 배포의 확정 모델이 아니었다.

**초기 입력·출력:** 서버의 전체 문맥 상한은 4096토큰, 출력 상한은 512토큰으로 시작한다. 입력은 모델의 실제 chat template·특수 토큰을 포함해 최대 3584토큰이다. 입력과 출력 상한의 합이 4096을 넘지 않게 한다. 모델의 최대 지원 길이를 그대로 허용하지 않는다. 이 수치는 시작 설정이며 성능 보장이 아니다.

**API 제약:** 사용자는 질문만 전달한다. 모델 ID, system prompt, sampling 값, context 길이, max_tokens, 응답 개수 n을 임의로 덮어쓰지 못한다. 응답은 하나(n=1), 도구 실행은 비활성화한다. 초기 평가와 일반 요청은 temperature=0으로 두되 동일 출력의 절대적 재현성을 보장한다고 설명하지 않는다. 모델·토크나이저 revision과 이미지 digest는 초기 실행 검증 후 고정하고 벤치마크마다 함께 기록한다.

**입력 초과:** 임베딩의 512토큰 한도와 생성의 3584토큰 입력 한도를 각각 검사한다. 사용자 질문 자체가 허용 한도를 넘으면 입력 오류를 반환한다. 근거 때문에 넘으면 ADR-014대로 낮은 순위 청크를 제외한다. 사용 가능한 근거가 있지만 한 개도 예산에 넣지 못하면 context_budget_exceeded로 실패시키며 근거 없음으로 오인시키거나 근거 없는 생성을 수행하지 않는다.

**출력 초과:** 512토큰을 채워 종료되면 done의 종료 이유를 length로 기록한다. 이것은 전송 성공과 별개로 답변이 잘렸을 수 있다는 뜻이다. 자동으로 두 번째 생성을 이어붙이지 않고 평가 시 잘림 비율을 기록한다. 정상적인 모델 종료는 stop으로 구분한다.

**대안:** 더 작은 모델, 큰 7B 이상 모델, 양자화 모델부터 시작. 처음에는 모델 하나의 실행·품질·성능을 검증하고, 품질 부족이 검색·prompt 문제가 아닌 모델 한계로 확인되면 교체를 검토한다.

**검증:** 서버 기동, 한국어 답변과 출처, 근거 없는 질문, 한도 경계, 출력 잘림, 스트리밍 취소, 동시 실행 2개에서 메모리 사용을 확인한다. temperature=0이라도 모델이 사실을 보장하지 않으므로 한국어 평가를 수행한다.

**재검토 조건:** 근거가 올바른데도 한국어 답변 품질이 부족하거나 출력 잘림·입력 제외·메모리 부족이 반복되는 경우. 한도·모델을 변경할 때 이전 설정과 같은 조건으로 재측정한다.

**출처:** [Qwen3-4B-Instruct-2507 공식 모델 설명](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507). 24GB 장비 기준과 4096/512 설정은 프로젝트의 제안이며 모델 제공자가 보장한 성능 수치가 아니다.

## ADR-016 — 4주 예산 상한

**기록일:** 2026-09-10. **상태:** 합의

**결정:** 4주 전체 상한은 100,000원, 지출 목표는 60,000~80,000원이다. GPU 45,000원, CPU 서버 30,000원, 저장소·부대 자원 10,000원, 세금·수수료·실험 예비비 15,000원으로 배분한다. 총액 안에서 항목 간 조정하며 2~4주 연장 비용은 별도로 검토한다.

**이유:** 평소 개발과 모의 테스트에는 GPU가 필요하지 않다. 실제 배포·성능 실험 때 집중해서 빌리고 초기 시행착오 비용을 남긴다. 매일 개발하는 시간을 모두 GPU 과금 시간으로 잡지 않는다.

**대안과 제약:** 상시 GPU 운영은 초기 목표에서 제외한다. GPU 총 40~60시간은 계획 가정이며 충분하다는 보장이 아니다. 공개 단가에 저장소·IP·세금·미청구 비용을 더해 확인한다. 예산 합의는 서버 구매나 자원 생성 완료를 뜻하지 않는다.

**재검토 조건:** 실제 대여 조건에서 총액을 맞출 수 없거나 연장이 필요한 경우. 예산을 자동으로 늘리지 않고 실험 시간·배포안을 먼저 조정한다. [계산 근거](../cloud-options.md)와 [운영 규칙 제안](../superpowers/specs/2026-09-10-llm-serving-lab-contracts.md)을 참고한다.

## ADR-017 — 세부 운영 계약과 구현 순서 승인

**기록일:** 2026-09-10. **상태:** 합의

**결정:** API·SSE 응답 형식, 파일·요청 크기, 작업 권한·복구 시간, 메모리 기반 속도 제한, Locust 측정 방식과 비용 관리 규칙을 보완 명세의 초기값으로 승인했다. 서빙 경계→문서와 RAG→운영 검증→성능 실험 순서로 작은 TDD 단위를 실행한다.

**이유와 제약:** 구현 중 서로 다른 해석을 줄이고 실제 실패를 하나씩 검증하기 위해서다. 제한값은 측정된 최적값이 아니다. 원격 업체·이미지 호환성·자원 크기는 첫 배포 시험으로 확인하고 결과를 기록한다. 설계 승인은 모델 기동이나 성능 검증 완료를 뜻하지 않는다.

**재검토 조건:** 실제 자원 한도·장애 시험·한국어 평가에서 가정이 맞지 않는 경우. 변경 이유와 검증 결과를 기록하며 전체 예산과 보안 경계를 유지한다.

**관련 문서:** [승인된 운영 계약](../superpowers/specs/2026-09-10-llm-serving-lab-contracts.md), [단계별 구현 계획](../superpowers/plans/2026-09-10-llm-serving-lab.md).

## ADR-018 — 최신 정식 Python 계열로 변경

**기록일:** 2026-09-10. **상태:** 사용자 변경 요청 반영. 구현 계획의 기존 Python 3.12 선택을 대체한다.

**결정:** 애플리케이션은 표준 CPython 3.14를 사용한다. 확인한 최신 정식 패치는 3.14.7이다. 로컬·API·Worker·테스트 환경을 맞추며 패키지 선언은 `>=3.14,<3.15`, 배포 환경은 검증한 정확한 패치와 이미지 digest로 고정한다. free-threaded 빌드는 초기 범위에 추가하지 않는다.

**쉽게 설명:** 새로 만드는 프로그램의 바탕을 현재 정식으로 나온 버전에 맞춘다. AI 서버는 따로 포장된 프로그램이므로 그 안의 Python까지 억지로 같게 만들 필요는 없다. 두 프로그램이 약속한 방식으로 통신하는지 확인한다.

**근거:** 공식 지원표상 3.14는 bugfix 단계, 3.12는 security 단계다. 3.15는 아직 prerelease이므로 초기 배포 기준으로 선택하지 않는다. 3.14 지원 종료 예정은 2030년 10월이다. 최신 버전만으로 확장성이 보장되지는 않지만, 새 프로젝트의 유지보수 기간과 사용자 선호에 맞는다.

**호환성:** FastAPI와 Locust의 현재 PyPI 메타데이터에는 Python 3.14가 명시되어 있다. 이것은 모든 전이 의존성의 실제 설치 성공 증거가 아니다. Celery·DB 드라이버·tokenizer 등 전체 조합은 Task 1과 해당 기능 단계에서 설치·import·테스트로 확인한다. vLLM·TEI는 각 이미지가 지원하는 런타임을 사용한다.

**업데이트 정책:** 3.14의 보안·버그 수정 패치는 테스트 후 반영하고 이미지와 잠금 파일을 갱신한다. 새 minor 버전은 의존성·통합 테스트 후 별도 변경으로 다룬다. 호환성 문제가 있으면 원인과 해결안을 기록하며 자동으로 구버전으로 내리지 않는다.

**현재 상태:** 문서 기준 변경 완료. Python 설치, 기존 3.10 가상환경 삭제, 애플리케이션 코드 변경, 실제 패키지 조합 시험은 수행하지 않았다.
