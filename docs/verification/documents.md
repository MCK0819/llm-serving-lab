# 문서 접수·조회·삭제 검증

검증일: 2026-09-13. 대상: 구현 계획 6단계. GPU 없이 실행했다.

## 무엇을 만들었나

문서를 맡기는 접수 창구와 접수 장부를 만들었다. PDF 원본은 파일로, 누가 맡겼는지와 앞으로 처리할 일은 PostgreSQL에 저장한다. 아직 PDF를 읽어 답하는 단계는 아니다.

- 인증한 조직의 문서만 조회한다. 같은 조직에서는 함께 읽되 올린 사람만 삭제한다.
- 문서와 처리 작업을 하나의 DB 거래로 기록한다. 한쪽만 저장된 접수를 만들지 않는다.
- 동시에 접수해도 조직별 10개·전체 100개 미완료 한도를 넘지 않도록 DB 잠금을 사용한다.
- 파일 20 MiB·요청 21 MiB를 실제 받은 크기로 검사한다. 최소 여유 공간은 1 GiB다.
- 파일 저장·동기 큐 통신은 별도 스레드에서 실행해 API 이벤트 루프를 막지 않는다.
- 문서·작업·청크의 조직 연결을 DB 제약으로도 검사한다. 벡터 저장 공간은 384차원이다.

## 장애와 경계 조건

| 상황 | 확인한 처리 |
|---|---|
| 다른 조직이 문서 번호를 앎 | 조회·삭제 404 |
| 같은 조직의 다른 사용자가 삭제 | 403 |
| 업로더가 반복 삭제 | 204, 본문 없음 |
| 같은 시간에 생성한 목록 항목 | 시간+문서 번호 커서로 중복 없이 조회 |
| 잘못된 커서·multipart·파일 항목 | 안전한 입력 오류, 내부 경로 노출 없음 |
| 파일 용량 초과·PDF 아닌 내용·디스크 부족 | 거절 후 미완성 파일 정리 |
| Content-Length가 없거나 거짓 | 실제 수신량에 21 MiB 제한 적용 |
| 업로드 취소·정리 중 재차 취소 | 디스크 작업 종료를 기다리고 임시·완성 파일 모두 정리 |
| DB 거래가 확실히 실패 | 저장한 원본 제거, 안전한 503 |
| DB는 저장했지만 완료 응답 유실 | 새 거래에서 같은 접수 잠금 획득 후 결과 확인 |
| DB 저장 여부 확인도 불가 | 원본 보존, 503. 이후 정리 작업 필요 |
| Redis 연결 불가 | 문서·작업은 남고 접수 202 |
| 알림 지연·요청 취소 | 호출자 대기 최대 1초, 기존 전송이 끝날 때까지 추가 전송 생략 |

큐 서버 연결 불가 시험은 실제 Celery 클라이언트와 연결을 받지 않는 로컬 포트를 사용했다. 느린 전송·취소 경쟁은 제어 가능한 스레드로 재현했다. DB 완료 응답 유실은 실제 PostgreSQL 거래에 실패를 주입했고, 미확정 거래가 끝나기 전에 파일을 지우지 않는 경쟁 조건도 검사했다.

동기 전송 스레드를 강제로 종료하지는 않는다. OS의 이름 조회 등이 지연돼도 동시에 남는 알림 전송은 하나이며 HTTP 대기에는 1초 제한이 있다. 정상 Redis 운영·Worker 복구를 검증한 것으로 해석하지 않는다.

## 환경과 재현

Python 3.14.7, Linux Docker, PostgreSQL 17/pgvector 0.8.6. 의존성 버전과 해시는 잠금 파일, DB 이미지 digest는 `deploy/compose.test.yaml`에 고정했다. 기존 의존성 버전은 유지하고 python-multipart 0.0.32, pgvector 0.5.0, Celery 5.6.3과 Redis 전송 의존성을 추가했다.

[개발 안내의 PostgreSQL 통합 테스트](../development.md#postgresql-통합-테스트) 명령으로 재현한다. 테스트 DB는 외부 포트를 열지 않고 임시 저장소를 사용한다.

마이그레이션은 `0002`에서 `0001_users`로 되돌린 뒤 다시 올렸고, `alembic check`에서 스키마 차이가 없었다. DB에서 pgvector 0.8.6과 `chunks.embedding`의 `vector(384)`를 확인했다.

최종 결과:

- Windows 단위 테스트와 실제 TCP 스트리밍 시험: **129개 통과**.
- Linux 단위·통합 전체: **172개 통과**. 실제 PostgreSQL 저장소 21개, 문서 API 17개 포함.
- Ruff 검사·포맷, mypy, pip check 통과.
- 실행 이미지 재빌드 후 UID 10001, 업로드 디렉터리 쓰기, DB 없이 liveness 200 확인.
- 검증용 DB 컨테이너와 내부 네트워크 종료·제거. 실제 GPU 대여 없음.

코드 검토에서 확인한 알림 취소와 반복 업로드 취소 문제는 재현 테스트가 먼저 실패하는 것을 확인한 뒤 수정했다. 최종 검토에 남은 수정 요구는 없다.

## 남은 범위

PDF 파싱·청크·임베딩은 7단계, Worker와 작업 복구·원본 청소는 8단계, RAG 연결은 9단계다. 원격 GPU 배포는 아직 미완료다. 요청 속도 제한·운영 지표·백업 복원 검증도 후속 단계이며 이번 테스트는 GPU 성능이나 운영 준비 완료를 증명하지 않는다.
