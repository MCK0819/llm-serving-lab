# 문서 처리 Worker와 중단 복구

문서를 접수하는 API는 접수증을 발급하고, 별도 작업자(Worker)가 내용을 읽어 검색용 벡터를 만든다. 작업자가 갑자기 종료돼도 접수 기록은 PostgreSQL에 남는다. 복구 담당 프로세스가 이 기록을 확인해 다시 처리하도록 알린다.

## 처리 규칙

| 상황 | 동작 |
|---|---|
| 같은 문서의 알림이 여러 번 도착 | DB에서 처리 권한을 얻은 시도만 작업 |
| 정상 처리 | 텍스트 추출 → 청크 → CPU TEI 임베딩 → 청크 저장과 ready 전환을 한 트랜잭션으로 완료 |
| 작업자 중단 | 처리 권한이 만료된 뒤 다음 시도가 이어받음 |
| 오래된 작업자가 뒤늦게 결과 제출 | 시도 번호·만료 시간·삭제 여부를 다시 확인해 거절 |
| 처리 중 문서 삭제 | 기존 작업이 문서를 되살리지 못함 |
| Redis 알림 실패 | DB 접수는 유지하고 다음 복구 스캔에서 다시 알림 |

처리 권한(lease)은 120초이고, 작업자는 20초마다 연장한다. 한 시도의 절대 제한은 300초이며 Celery의 Linux 자식 프로세스 시간 제한도 적용한다. 첫 실패 후 10초, 두 번째 실패 후 30초 이상 기다리며 최대 세 번 시도한다. 강제 종료된 시도도 횟수에 포함한다. 복구 스캔 주기는 30초이므로 대기 시간은 정확한 재시작 시각을 보장하지 않는다.

PDF 분석과 토크나이저 초기화는 처리 권한을 얻은 뒤 별도 스레드에서 실행한다. 이 동안 비동기 heartbeat가 계속 동작한다. Python 스레드는 취소만으로 강제 종료되지 않으므로, 멈춘 분석의 최종 격리는 Celery 프로세스 제한이 맡는다. Worker 동시성은 1이고 선점 알림 수는 1이다.

## 파일 정리와 보안

삭제된 문서의 파일과 청크는 정리 프로세스가 제거한다. DB에 없는 `.pdf`와 `.part`는 한 시간이 지난 뒤 정리한다. 업로드부터 DB 기록이 끝날 때까지 운영체제 파일 잠금을 유지하므로, 오래 걸리는 업로드를 고아 파일로 잘못 지우지 않는다. 취소 중 잠금을 얻은 경우에도 파일 핸들을 닫는다.

작은 `.upload` 잠금 파일은 남겨 둔다. 이를 지우고 새로 만들면 서로 다른 파일에 잠금이 걸릴 수 있기 때문이다. 파일 이름에는 원본 이름 대신 조직·문서 UUID를 사용한다. API와 Worker는 같은 업로드 볼륨을 공유하며 각자의 루트 아래 동일한 UUID 경로를 사용한다.

작업 알림에는 문서 번호만 넣고 조직은 DB에서 확인한다. 손상된 PDF를 읽는 라이브러리 경고에 원문이 섞일 수 있어 Worker는 해당 경고의 외부 출력을 막는다. 앱은 제한된 오류 코드만 기록한다.

## 선택한 절충

Redis는 접수 장부가 아니라 작업자를 깨우는 알림 통로다. 전용 Redis의 메모리를 64 MiB로 제한하고 `noeviction`을 사용한다. 꽉 차면 새 알림을 거절하며 DB 복구 스캔이 나중에 다시 시도한다. 오래 쌓인 중복 알림은 새 작업을 늦출 수 있다. 이번 단계에서는 분산 중복 제거 장치를 추가하지 않고 메모리 상한과 DB 처리 권한으로 자원과 정합성을 보호한다.

## 검증 범위

단위 테스트는 GPU 없이 파싱·임베딩 오류, 초기화 실패, heartbeat 상실, 취소, PDF 원문 로그 차단을 확인한다. 실제 PostgreSQL 시험은 중복 claim, 오래된 결과 제출, 재시도 소진, 처리 중 삭제, 파일 정리 실패 후 재시도를 확인한다.

별도 Linux 시험은 실제 Redis와 Celery prefork Worker를 사용한다. 시험이 만든 Worker 프로세스만 강제 종료하고, DB 시간을 조정해 만료를 재현한 뒤 새 Worker가 한 번만 결과를 저장하는지 확인한다. 임베딩 서버는 제어 가능한 HTTP 시험 서버이므로 이 시험의 시간은 모델 성능 수치가 아니다. 실제 CPU TEI 검증은 [앞 단계 기록](document-processing.md)과 구분한다.

고정 토크나이저 캐시를 준비하고 Docker Desktop의 Linux 엔진에서 다음 명령으로 재현한다. 시험 전용 PostgreSQL·Redis만 생성하며 운영 스택에는 연결하지 않는다.

```powershell
$env:LLM_LAB_TEST_DB_PASSWORD = [Guid]::NewGuid().ToString("N")
try {
    docker compose -f deploy/compose.worker-test.yaml up --build --abort-on-container-exit --exit-code-from test
    if ($LASTEXITCODE -ne 0) { throw "Worker recovery tests failed" }
} finally {
    docker compose -f deploy/compose.worker-test.yaml down
    Remove-Item Env:LLM_LAB_TEST_DB_PASSWORD
}
```

2026-09-14 로컬 회귀 시험은 212개 통과했다. Linux/PostgreSQL 전체 시험은 269개 통과했고, 모델 환경 또는 별도 프로세스 환경이 필요한 8개는 해당 실행에서 제외했다. 별도 프로세스 시험은 두 개 모두 통과했다(35.56초). Worker 강제 종료 후 두 번째 시도가 `ready`와 청크 한 개를 저장했다. 다른 시험은 접수 API에 닫힌 Redis 포트를 지정해 실제 연결 실패를 만들고, 정상 Redis에 연결한 복구 프로세스가 남은 DB 작업을 처리하는지 확인했다. Redis 서버 자체를 재시작한 시험과는 구분한다.

| 강제 종료 시험의 관측 지점 | 시험 시작부터 경과 시간 |
|---|---:|
| 첫 Worker가 처리 시작 후 HTTP 임베딩 서버 도달 | 8.601초 |
| DB 복구 스캔이 알림 재전송 | 10.978초 |
| 새 Worker가 두 번째 시도 시작 | 19.721초 |
| ready 및 청크 한 개 확인 | 20.149초 |

위 시간은 Docker Desktop의 Linux 컨테이너에서 CPU 2개·메모리 2 GiB로 실행한 기능 시험 기록이다. 대기 시간을 줄이기 위해 lease를 DB에서 과거로 조정했으며, 운영 복구 시간이나 처리 성능 보장이 아니다. 원격 GPU 생성, RAG 답변 연결, 부하 시험은 이번 단계에 포함하지 않는다.

Ruff·포맷·mypy·의존성 검사는 통과했고, Alembic 스키마 차이는 없었다. 애플리케이션 Compose 설정 검증, API·Worker·복구·마이그레이션 이미지 빌드, 배포 이미지의 Worker CLI 실행을 확인했다. 실제 TEI를 포함한 운영 Compose 전체를 함께 기동하는 시험은 이번에 수행하지 않았다. 운영 Redis 메모리 제한도 설정 검증이며 실행 중 측정값은 아니다. 시험용 컨테이너와 임시 비밀값은 정리했다.
