# 요청 제한과 안전한 종료

여러 사람이 사용하는 창구에는 한 사람이 너무 많은 일을 맡기지 못하도록 접수 제한이 필요하다. 문을 닫을 때도 새 접수는 멈추고, 이미 받은 일에는 마무리할 시간을 준다. 이번 단계는 이 두 규칙과 민감정보 보호를 구현한다.

## 요청 횟수 제한

인증된 사용자마다 최근 60초 동안 질문 20회, PDF 업로드 3회, 문서 조회·삭제 60회를 허용한다. 문서 목록도 조회 횟수에 포함한다. 제한을 넘으면 `429 rate_limited`와 다시 시도할 때까지의 초를 담은 `Retry-After`를 반환한다. 정각마다 초기화하는 방식이 아니라 매 요청 시점에서 지난 60초를 센다.

인증 뒤, 본문 분석이나 모델 호출 전에 제한을 확인한다. 따라서 인증된 사용자의 잘못된 질문 본문이나 PDF 업로드 시도도 횟수에 포함된다. 사용자별로 계산하므로 같은 사용자의 키를 새로 발급해도 한도를 공유한다.

현재 API 프로세스 하나의 메모리에 기록한다. 프로세스를 재시작하면 기록이 사라지고, 여러 프로세스를 실행하면 각자 별도의 한도를 갖는다. 배포 명령은 프로세스 하나를 사용한다. 사용자·요청 종류 조합은 최대 10,000개이며, 공간이 찼을 때 만료된 기록을 정리한다. 그래도 꽉 차면 새 조합을 거절한다. 이는 인증 전 공격이나 여러 서버에 걸친 제한까지 해결한 것은 아니다.

## 상태 확인

- `/health/live`: 웹 프로그램이 응답하는지 확인한다. 정상 응답은 200이다.
- `/health/ready`: DB 조회, 업로드 경로의 실제 쓰기·삭제 가능 여부, 종료 중 여부를 확인한다. 접수 가능하면 200, 불가능하면 503이다.

GPU나 Redis가 멈춰도 DB와 파일 저장소가 정상이라면 접수 준비 상태를 유지한다. 문서 접수 장부는 DB에 남기고, 모델 호출 실패는 해당 질문에서 처리한다. 동시에 여러 준비 상태 요청이 와도 진행 중인 검사 하나를 공유하며 각 요청은 최대 2초 기다린다. 응답에는 내부 주소나 오류 원문을 넣지 않는다. 의존성별 지표와 대시보드는 12단계에서 추가한다.

## 종료 절차

Docker의 API 실행 명령은 `python -m app.server`다. 종료 신호를 받으면 새 작업은 503, 준비 상태는 503을 반환한다. 이 동안 생존 확인은 200이다. 기존 작업에는 신호 시점부터 최대 30초를 주고, 남은 작업을 취소한 뒤 연결을 정리한다. 취소 정리에 3초, 웹 서버와 애플리케이션 종료에 추가 5초의 상한을 둔다. Docker의 외부 종료 유예는 40초다.

개발용 `uvicorn app.main:create_app --factory` 명령은 이 종료 조정 서버를 사용하지 않는다. 운영 종료 동작은 Docker 실행 명령으로 확인해야 한다. `app.server`는 컨테이너에서 사용할 수 있도록 `0.0.0.0:8000`에 바인딩한다. 호스트 공개 범위는 Docker 포트 매핑과 방화벽에서 제한한다.

취소는 Python 스레드나 멈춘 운영체제 작업을 강제로 중단하지 못한다. 이런 상황의 최종 상한은 Docker가 40초 뒤 프로세스를 강제 종료하는 설정이 맡는다. 강제 종료 시 완료되지 않은 문서 작업은 DB 처리 권한과 기존 Worker 복구 규칙을 따른다.

## 로그와 오류 응답

질문·PDF 원문·인증키·상위 모델 서버의 오류 본문을 로그에 기록하지 않는다. HTTP·SQL·PDF 라이브러리와 웹 서버의 원문 출력을 제한하고, 예상하지 못한 요청 실패는 `request_failed`와 요청 식별자로 남긴다. 웹 서버 오류는 제한된 코드로 기록한다. 응답에서도 내부 예외 내용을 숨긴다.

이 선택은 정보 유출 위험을 줄이지만 상세한 장애 원인을 추적하기 어렵게 한다. 이후 관측 기능도 승인된 오류 종류·시간·건수 중심으로 추가해야 한다. 이미 시작된 스트림에서 예외가 나면 성공 완료 이벤트를 만들지 않고 연결을 끝낸다. 클라이언트는 완료 이벤트가 없는 응답을 미완료로 처리해야 한다.

## 검증 기록

2026-09-17 최종 로컬 단위·요청 제한 API·실제 소켓 회귀 테스트는 총 253개 통과했다. 60초 경계, 사용자·종류별 분리, 저장 공간 상한, 안전한 오류 응답, 취소와 로그 보호를 포함한다. 검토 중 잘못된 문서 ID·조회 조건이 요청 제한을 건너뛰는 문제를 재현했다. 인증 직후 입력 검증보다 먼저 횟수를 세도록 수정하고 회귀 시험과 재검토를 통과했다.

Linux/PostgreSQL 전체 시험은 316개 통과, 12개 제외였다. 실제 DB 인증을 거친 질문·잘못된 JSON·잘못된 PDF 업로드·상위 서버 오류에서 민감정보가 응답과 로그에 없는지 확인했다. 제외 항목 중 Docker 종료 두 개와 Worker 프로세스 두 개는 별도 실행으로 모두 통과했다. 나머지 여덟 개는 실제 CPU TEI 환경이 필요한 시험으로 이번에는 다시 실행하지 않았다.

| 실제 프로세스 시험 | 결과 |
|---|---|
| 종료 신호 후 기존 답변 정상 완료 | 1.106초 후 종료, 상위 연결 정리 |
| 응답이 끝나지 않아 30초 기한 도달 | 30.876초 후 종료, 상위 연결 정리 |
| Worker 강제 종료 후 재처리 | 두 시나리오 통과, 강제 종료 복구 시험은 시작 후 16.978초에 완료 |

종료 시험은 시험 전용 HTTP 모델 서버와 실제 TCP 연결을 사용했다. Worker 시험은 복구를 재현하기 위해 DB의 처리 권한 만료 시각을 조정했다. 위 시간은 기능 검증 기록이며 실제 GPU 성능이나 운영 복구 시간 보장이 아니다.

배포 이미지 빌드, 기본 서버 명령의 생존 확인과 정상 종료, 일반 사용자 UID 10001 실행, Compose 설정 검사도 통과했다. 시험용 컨테이너와 네트워크를 정리했고 모델 캐시는 유지했다. 전체 실제 모델 운영 스택은 실행하지 않았다.

종료 시험은 Docker Desktop Linux 엔진에서 다음처럼 재현할 수 있다. 시험이 만든 컨테이너에만 종료 신호를 보내며, 포트는 로컬 주소에만 공개한다.

```powershell
docker build -f deploy/Dockerfile.test -t llm-serving-lab:shutdown-test .
$env:LLM_LAB_SHUTDOWN_TEST_IMAGE = 'llm-serving-lab:shutdown-test'
try {
    .venv314/Scripts/python.exe -m pytest tests/integration/test_shutdown.py -q
} finally {
    Remove-Item Env:LLM_LAB_SHUTDOWN_TEST_IMAGE
}
```

전체 PostgreSQL 시험은 [개발 안내](../development.md), Worker 프로세스 시험은 [중단 복구 기록](worker-recovery.md)의 재현 명령을 따른다.
